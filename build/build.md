# build — 构建规则（怎么造 spec 和模块）

> 本目录是「构建规则」层（即 L0——最底层的构建规则，云端唯一事实源）：回答「spec 和
> 模块长什么样、怎么造、怎么组合、怎么溯源」。**默认不读**：日常执行任务
> （判定入口、走模块）不读本目录；只有「设计或修改 spec / 模块」时才读。
> 日常要读的是「使用规则」——仓库根 `AGENTS.md`、各 spec 的 `AGENTS.md`、
> 各模块的 `MODULE.md`。
>
> 需造 / 改 spec 或模块时，按模板框架 `spec/AGENTS.md` 的指引拉取本目录到
> 项目 `spec/build/`（拉取是主动动作；项目通常不需要它）。

## 一、规则分两类：构建规则 vs 使用规则

一套项目里同时存在两类规则，性质相反，别混：

| | 构建规则 | 使用规则 |
| --- | --- | --- |
| 回答什么 | 怎么**造** spec 和模块 | 怎么**用** spec 和模块 |
| 读者 | 设计 / 修改 spec 模块的人或 agent | 日常执行任务的人或 agent |
| 默认读不读 | **默认不读**（只在造 / 改时读） | **默认要读**（每次任务都读） |
| 落点 | 云端 `build/`（拉取到项目 `spec/build/`） | 根 `AGENTS.md`、spec 的 `AGENTS.md`、模块的 `MODULE.md` |
| 命名 | 非 `AGENTS.md`（避免被各软件自动扫描误读） | `AGENTS.md`（本就该被自动读到） |

一句话：**构建规则是「说明书怎么造」，使用规则是「说明怎么用」**。造 spec /
模块时才翻开前者，日常干活只靠后者。

## 二、三层体系（这套东西怎么分层）

```
构建规则（本目录，云端 SSOT、按需拉取）
   ↓ 照着造
spec 包（从云端拉取；单项目单 spec）
   ↓ 增补
项目补丁（纯增量：加私有模块、fork 内置，不改内置本体）
```

- **构建规则**：本目录，spec 无关——任何 spec 都照它造。
- **spec 包**：具体一套工作流（如 software-dev），从云端拉取例化。
- **项目补丁**：项目对 spec 的增量修改，靠锁文件的 `source` 字段标记
  （`private` / `fork`）。

来源是两层的：spec 与模块都从云端模块库来。溯源统一归锁文件
（`spec/lockfile.md` 讲字段，`spec/lockfile.py` 生成校验，均在模板框架
`spec/` 出厂自带），不在 spec / 模块文件里重复记。

## 三、模块形态：一个模块一个目录

两种布局别混：**云端存储形**——本仓存 `modules/<模块 id>/`（无 `@`）；
**项目例化形**——拉取进项目后是 `spec/<spec id>/@<模块 id>/`（`@` 前缀
例化时才加）。目录内部结构相同：

```
<模块 id>/                      ← 一个模块一个目录（例化后目录名 = @ + id）
  MODULE.md                     ← agent 规范（开头声明适用范围）+ 产物目录与例化
  module.json                   ← 结构化声明（机器读；10 字段表见模板 spec/AGENTS.md）
  README.md                     ← 给人读：一句话定位 + 适用与边界 + 启用/停用
  CHANGELOG.md                  ← 版本变更日志（跨版本迁移看它）
  assets/                       ← 附件（模板 / 清单 / 脚本，随模块走）
```

新建模块：复制 `module-template/` 目录，改名为 `模块 id` 放进 `modules/`，
替换 `<占位符>`，按字段表填 `module.json`。三步：① 复制改名 → ② 填
`module.json` → ③ 改写 `MODULE.md` 与 `README.md`。

## 四、模块命名规则

- **例化目录名 = `@` + id**：`@` 只作模块例化进项目后的目录标识，让人一眼
  认出模块目录；模块 id 不含 `@`（`module.json` 的 `id` 是 `vision`），
  云端 `modules/` 下的目录名就是纯 id。
- **id 用连字符小写命名**（kebab-case：全小写、单词间用 `-` 连接，如
  `software-dev`、`@vision`），与目录名（去 `@` 后）一致。
- **模块规范叫 `MODULE.md`**（不叫 `AGENTS.md`）：模块规范是按需读的，叫
  `AGENTS.md` 会被各 agent 软件按不同策略自动扫描，改 `MODULE.md` 靠指针主动
  加载，行为可控。

## 五、粒度判据与模块独立性（什么算一个模块、模块怎么自持）

三条同时满足才拆成独立模块：**跨场景复用**（不只一个场景用）、**独立启停**
（能单独启用停用）、**输入输出隔离**（有明确输入与产出）。不满足就并进现有
模块，或留给框架，不硬拆。

**模块是独立能力，编排归 spec 层**：模块 = 输入 → 运行过程 → 产出，自持
自解释，不感知其他模块——内部描述如非必要不提其他模块（提模块名、提他
模块的产物路径都算提及；通用词不算）。谁依赖谁、什么顺序跑、哪里设检查
点，是编排，一律由 spec 的 `AGENTS.md`（依赖全景图 + 入口）表达，模块
不背编排。`module.json` 的 `depends_on` 只记强依赖（不依赖对方模块就
无法运转才写，如 release 依赖 audit），默认为空。

## 六、spec 包形态与入口缩放

- **spec 包形态**（项目例化形）：一个 spec 包 = 组织清单（`manifest.json`）
  + 入口指引（`AGENTS.md`）+ 模块目录（`@模块`）；云端存储形只有
  `specs/<id>/` 三文件（清单 + 入口 + 变更记录），模块在 `modules/` 下
  独立存放，例化时才复制进包。文件结构、字段表、命名、状态灯、
  空值等**机制通则的单一来源在模板框架 `spec/AGENTS.md`**（出厂自带），
  spec 包的 `AGENTS.md` 只写本包运转（这是什么 + 依赖全景 + 入口判定）。
- **入口缩放**：一套 spec 该定义**多个入口**，不同等级的任务从不同入口进、
  启用不同模块子集——简单的事不背重流程，复杂的事不漏环节。入口定义（启用
  哪些模块）在 `manifest.json` 的 `entries`（集合、不表顺序）；入口判定语义
  在 spec 的 `AGENTS.md`；模块间依赖与执行顺序用一张 mermaid 全景图表达
  （放 spec 的 `AGENTS.md`，编排归 spec 层，见第五节）。
- **检查点归 spec 层**：哪里设检查点是编排，由各 spec 的 `AGENTS.md` 声明。
  按控制权设：协作产出段（与用户反复讨论，天然处处确认）不设显式检查点；
  显式检查点只设在控制权交接处——如「实施放行」（agent 转全权执行前）与
  「收口放行」（发布等不可逆动作前）。

## 七、版本号规则与 CHANGELOG

**版本号（SemVer）**：模块与 spec 的 `version` 遵循语义化版本，格式
`主.次.修订`（如 `0.1.0`）：

- **主版本（首位）**：不兼容的变更才 +1（改了别人依赖的接口 / 行为），+1 时
  次、修订归零；
- **次版本（中位）**：向后兼容的新增才 +1（加新功能、加新模块）；
- **修订号（末尾）**：向后兼容的修复才 +1（改 bug、改措辞）；
- **主版本为 0**：开发期，接口不稳定，任何版本都可能变，不做兼容承诺；1.0.0
  起才承诺接口稳定。

**CHANGELOG**：每个模块和 spec 都带 `CHANGELOG.md`，按版本记录变更（分类参考
Keep a Changelog：Added / Changed / Removed / Fixed）。跨版本迁移时，agent 读
它就知道「从旧版迁到新版要注意什么」，不兼容的变更（主版本 +1）必须写清。

## 八、本目录内容

```
build/
  build.md                ← 本文件
  spec-template/          ← spec 模板（造新 spec 骨架：AGENTS.md + manifest.json 空例）
  module-template/        ← module 模板（造新模块骨架）
```

**不包含**：锁文件工具与字段规范（家在框架 `spec/lockfile.py` / `lockfile.md`，
随模板出厂）。
