## 【通用】仓库布局与文件分类归属（三区，强制）

| 区 | 位置 | 内容 | 版本管理 |
|---|---|---|---|
| A. 公开 | 仓库根、`src/`、`docs/`、`scripts/`、`.github/`、`archive/` | 用户可见、可发布、无敏感信息（含归档区） | 主仓库 git，发布到 GitHub |
| B. 私有 | `private/` | 个人/机器专属信息、开发期文档（PRD/RFC/ADR/RESEARCH 登记册、PROTOTYPE（页面原型/设计稿）、DESIGN/CHANGELOG/TEST-REPORT/STATUS/经验文档）、测试素材 | private 子 git（本地、无远端） |
| C. 不管理 | 各处 | `node_modules/`、`dist/`、`build/`、日志、缓存、临时文件、`_trash/` | 无（.gitignore 忽略） |

**归属判定规则**（新增文件必须先判区再落盘）：

1. 含**个人/机器专属信息**或**发布前不公开**内容 → B（`private/`）；
2. **生成物/缓存/可重建**内容 → C（不版本管理）；
3. 用户可见、可发布、无敏感信息 → A（主仓库）；
4. **密钥/凭据绝不入库**：`.env`、`*.key`、`*_secret*` 等一律进 `.gitignore`；
   确需保留的密钥只放 `private/`（且不提交 private 子 git，或加密后提交）。

**发布前检查**：主仓库 `git status` 只应出现 A 区文件；`git -C private status`
负责 B 区；C 区内容两者都不得出现。发布前必须先同步 private 子 git
（见「发布流程」与 `scripts/pre_release_check.py`）。

## 【通用】Agent 启动 / 恢复协议（每次新对话、任何 agent 都按此 bootstrap）

1. **必读**：读本文件（红线 + 加载规则）→ `private/AGENTS.md`（开发入口与完整规范）→
   `private/dev/STATUS.md` 快照（判断当前阶段/进度）。
2. 查看两个仓库状态：`git status`（主仓库）、`git -C private status`（私有子 git）。
3. **按需读**：`version.json` 与 `private/dev/CHANGELOG.md` 顶部（版本与最近变更）、
   `private/dev/DESIGN.md` 与 `TEST-REPORT.md`、进行中需求/方案/决策的登记册 INDEX。
4. **阶段恢复**：按 STATUS 快照「📇 阶段卡」判断当前阶段 → 按「任务影响清单 → 要读
   文档清单」逐份读（详见 `docs/LOADING.md` 恢复协议）；阶段卡缺失时 `git log` 推断、
   仍不确定则询问用户。
5. **上下文压缩后或任何新对话开始时，必须先完成以上重读（红线 16），不得凭记忆
   直接继续。**
6. 任何实施开始前，必须先走阶段体系：**对齐需求与计划、获用户确认**（P1 需求 /
   P2 方案为决策型，须用户确认放行）。

## 【通用】开发工作流（阶段体系摘要；权威定义见 `private/dev/PHASES.md`，流程图见 `docs/FLOW.md`）

**5 大阶段串行**（16 节点收敛，每次只专注一个，严禁跨阶段）：

| 模块 | 节点 | 类型 | 明确产物 | 退出条件 |
|---|---|---|---|---|
| P1 需求 | 01-05 | 🔵决策 | PRD 定稿 + RESEARCH | 阶段卡 + **用户确认** |
| P2 方案 | 06-09 | 🔵决策 | RFC / ADR / 原型 / DESIGN | 阶段卡 + **用户确认** |
| P3 开发 | 10-11 | 🟢执行 | 实现代码 + 文档就绪 | 展示阶段卡，无反对即继续 |
| P4 审计验证 | 12-13 | 🟢执行 | 审计结论 + TEST-REPORT | 展示阶段卡，无反对即继续 |
| P5 交付发布 | 14-16 | 🟠发布 | commit / tag / Release / EXP | 展示阶段卡；发布另行确认 |

- **P1 需求引导（强制）**：先复述意图、提开放问题帮用户澄清真实需求，**未澄清前禁止
  直接抛方案选项**（「技术决策先解释后选择」）；立项类话题先按红线 14 GitHub 调研并
  提醒「先调研再立项」；提问遵守红线 18（禁面板 / 回答重检 / 重检行 / 共识卡）。
- **涉及界面/交互、架构/结构、流程/状态的改动**：先出图（页面原型/架构图/流程图，
  见 PHASES.md P2）向用户展示、获确认后才实施。
- **档位**：S 档 P1 简化直达 P3；M 档 P1 全走（RFC 可选、ADR 架构级必走）；L 档全走。

**阶段卡展示（每次对话强制）**：实质回复/阶段落盘/恢复/收尾/用户询问进度时，展示
**合并紧凑阶段卡**（标题含状态 + 横置阶段线（当前节点加粗）+ 合规两行 + 反定型
紧凑内容（**仅关键/风险节点**）；格式见 `private/dev/PHASES.md` §5）；**阶段卡内一律
使用中文名称，不显示字母缩写**（如 需求阶段/方案文档/架构决策记录/状态快照）；以
`private/dev/STATUS.md` 为单一真相；决策型推进前，阶段卡附 **📌 共识卡**（认知基线/
缺口/质疑/推进结论，用户逐项表态，红线 18）。**每次阶段/子阶段完成：落盘 STATUS → 展示阶段卡
→ git 提交（主仓库 + private 子 git，提交信息带阶段标识）。**

## 【通用】自动审计（实施后必做；清单见 `docs/audit-checklist.md`）

实施完成后、提交前，必须自动审计：**自审**（按 `docs/audit-checklist.md` 逐项核对）
→ **独立审计（推荐）**（委托独立子 agent / 独立会话，只看 `git diff` 与审计清单）
→ **修复与复检**（修复影响面大时再次审计）→ 审计结论记入最终汇报。

## 【通用】通用红线（Agent 开发，强制）

1. **要求三要素（意图 / 展示 / 验收）**：对 AI 的任何红线/要求，定稿前必须同时
   具备三要素——**原始意图**（为什么有这个要求，防机械执行与误解）、**展示面**
   （执行情况在阶段卡/合规清单/交付汇报的哪里可见）、**验收面**（结果如何核对：
   能自测的自测，不能自测的交用户验收）；缺任一要素不得定稿。本红线自身按
   三要素书写：意图=不可展示、不可验收的要求 AI 倾向不做；展示面=每条红线的
   展示锚点在本文件及各流程文档中可见；验收面=审计清单与校验脚本按锚点核对。
2. **先对齐后实施**：
   - **意图**：未对齐即动手是返工与越权的主要来源。
   - 实施之前必须对齐需求和计划，得到用户确认之后再实施；未确认不实施（低风险
     例外见第 3 条）。
   - **展示面**：阶段卡确认节点 / 交付检查清单「需求已复述并获确认」；**验收面**：
     审计清单第 1 节人工核对。
3. **变更分级**：
   - **意图**：高风险操作出错代价大且常不可逆，需先知情同意；低风险不必事事打断。
   - 高风险操作（大规模影响文件、破坏性变更、永久删除、发布/推送、修改用户数据）
     先展示方案、征得用户同意后执行；低风险先执行、随后记录、告知用户并给出回退
     方案。
   - **展示面**：方案与回退方案随回复可见；**验收面**：审计清单「高风险已征得
     同意」。
4. **实施后自动审计**：
   - **意图**：实施者自带视角盲区，需要独立视角兜底。
   - 每次实施完成后按「自动审计」执行，优先独立子 agent / 独立会话审计（只看
     diff 与清单）。
   - **展示面**：审计结论写入交付汇报/测试报告；**验收面**：审计清单逐项核对 +
     独立审计结论。
5. **删除纪律**：
   - **意图**：误删不可逆，可恢复路径是底线。
   - 对话内删除先移动到项目本地 `_trash/<agent产品名>_<YYYY-MM-DD>_<HHMM>/`
     （临时删除区，如 `codex_2026-08-25_2330`；不设固定 agent 列表，以执行 agent
     的产品名为准），对话任务结束时用 `python scripts/trash.py` 将整轮文件夹
     **整体**移入回收站（避免小文件堆积）；严禁绕过工具接口的永久删除
     （`rm -rf` 等）；确需永久删除必须用户确认。
   - **展示面**：`_trash/` 目录命名可见；**验收面**：审计清单「删除均走可恢复
     路径」+ `trash.py` 状态可查。
6. **回读校验**：
   - **意图**：写入成功 ≠ 写盘成功（并行编辑/编码竞态可能显示成功但未落盘）。
   - 重要写入/修改/移动后回读核对内容与结构，缺失即补正；**同一文件多处并行编辑
     存在竞态（可能显示成功但未写盘），改完必须整篇回读抽查，不能只看 diff**。
   - **展示面**：回读结果在回复/阶段卡可见；**验收面**：审计清单「重要写入已回读」。
7. **创建前相似检查**：
   - **意图**：重复实现/重复文档污染仓库与上下文。
   - 创建新文件/内容前先搜索相似内容，高相似时由用户决策（合并 / 跳过 / 仍创建）。
   - **展示面**：创建说明附「相似检查」结论；**验收面**：审计清单「创建前做过
     相似检查」。
8. **信息以用户/事实为准**：
   - **意图**：臆造信息比承认不知道危害更大。
   - 不自行臆造；信息不足时询问补齐，不猜测；不确定处显式标注。
   - **展示面**：引用来源/标注不确定；**验收面**：审计清单「信息以用户/事实为准」。
9. **不破坏用户未提交的改动**：
   - **意图**：用户本地成果不得因 agent 操作丢失。
   - 不擅自回滚、reset、stash、覆盖用户未提交内容；不代为 `git init` 用户的其他
     仓库；不对共享分支 force push。
   - **展示面**：操作前状态快照/变更说明；**验收面**：审计清单「未破坏用户未提交
     改动」。
10. **private 目录纪律**：个人/开发期文件一律放 `private/`，主仓库绝不提交
   `private/` 内容；发布前必须先同步 private 子 git（见「发布流程」）。
11. **发布前验证**：检查与测试通过、TEST-REPORT 有记录、审计完成，才允许发布。
12. **密钥安全**：任何密钥/凭据不入主仓库（见「仓库布局」规则 4）。
13. **文档同步与治理**：
    - **意图**：文档与实现漂移会误导后续接手者；过时文档比没有文档更危险。
    - 改动涉及用户视角或流程时，受影响文档在**同一次改动**内更新；**发现过时
      立即修（不论是否本轮引入），无变更时也须校准状态文档**（如 STATUS「当前
      做到哪里」）；**文档正文 = 当前有效状态**——决策修改时直接覆盖原文、禁止
      保留旧段落或「已取代」标注、禁止 AI 在正文追加大段历史说明，确需留痕只在
      `private/dev/CHANGELOG.md` 记一行摘要；**例外：`private/dev/prd|rfc|adr|
      research/` 为历史文档区，允许正文留史**（PRD/RFC 定稿后冻结、ADR 只增不改、
      RESEARCH 发现记录只追加，按各自 `INDEX.md` 状态机维护）；废案直接删除
      （走 `_trash/` → `trash.py`），可恢复性由删除机制保证。
    - **展示面**：阶段卡合规「文档同步」项；**验收面**：审计清单第 3 节 +
      `check_dev_docs.py` 部分断言。
14. **立项调研先行**：
    - **意图**：从零造轮子通常是次优方案，先看现成参考再立项。
    - 讨论项目思路/需求/架构/功能/产品等**立项类话题**时，**优先在 GitHub 调研
      现成参考**（相似项目、方案、库），并向用户展示调研结果、提醒用户
      **「先调研再立项」**；未经调研不引导用户立项，不把「从零造轮子」作为默认
      方案。
    - **展示面**：调研记录（RESEARCH）随回复可见；**验收面**：审计清单「立项已
      调研」。
15. **阶段落盘**：
    - **意图**：进度只存对话记忆=上下文压缩即丢。
    - 任务过程中每完成一小阶段，先更新 `private/dev/STATUS.md` 快照与受影响文档
      再继续；进度不得只存在于对话记忆。
    - **展示面**：状态快照/阶段卡；**验收面**：`check_dev_docs.py` STATUS 断言 +
      审计清单「阶段落盘已完成」。
16. **上下文恢复重读**：
    - **意图**：凭记忆继续=按旧信息行动。
    - 上下文压缩后或任何新对话开始时，必须重读红线规范（根 `AGENTS.md` 与
      `private/AGENTS.md`）与相关文档（`STATUS.md`、`DESIGN.md`、`CHANGELOG.md`、
      `TEST-REPORT.md` 及受影响文档）后再继续；不得凭记忆直接继续。
    - **展示面**：恢复协议第一条回显已重读；**验收面**：审计清单「上下文压缩/新
      对话后已重读」。
17. **范围克制与纠错清零（按单办事、不加菜；撤菜不解释）**：
    - **意图**：让做番茄炒蛋，不得擅自加东坡肉；被指出后撤掉即可，不得在标题、
      提交信息、PR、注释或文档中为「未做/不做的事」补写说明（如「已移除多余的
      X」「为什么本项目不需要 X」）——防止无用信息堆积污染上下文。
    - **展示面**：交付/阶段落盘时展示本次 diff 影响文件清单；阶段卡合规「红线
      遵循」项列出「范围克制：diff 已核对」。
    - **验收面**：审计清单检查项 + 辩护性措辞扫描（提交信息/PR 描述命中硬拦，
      注释/文档命中人工复核清单）+ 用户核对 diff；确需留痕仅
      `private/dev/CHANGELOG.md` 记一行。
18. **提问与共识确认（禁面板 / 回答≠确认 / 共识卡 / 重检行）**：
    - 禁止调用问题面板/选择面板类结构化 UI 向用户提问（含 request_user_input /
      AskUserQuestionTool 类工具）；需要提问时只在聊天/文本中展示开放问题并中止
      对话等待用户输入。聊天内可给选项与推荐（信息辅助），但不得仅依赖选择项
      盲目向下推进，确认必须以用户自由文本的明确表态为准。
    - 用户回答 ≠ 需求确认：每次回答后作为新信息输入，重检问题空间并输出一行
      **重检行**（「重检：这条新信息改变了 X / 未改变 Y / 浮现新问题 Z」）。
    - **硬触发清单**（以下节点必须完整展示共识卡，无裁量）：需求方向调整、
      调研结论形成、定稿/采纳/放行前、验收标准变更、发现需求矛盾、范围变更。
    - **共识卡**（决策型推进前固定块，替代反定型条件块与共识快照）四项：
      ① 认知基线（当前理解 + 我的假设 + 已确认共识）② 缺口（尚未确认 +
      新浮现问题）③ 质疑（反例 + 替代解释）④ 推进结论（重新审视 + 本次需
      用户逐项表态项）；用户逐项表态后推进，不得 push 流程、不得诱导。
    - 确认不锁定：需求阶段内任何新信息可回到该流程重审；PRD 定稿后变更走
      变更流程（开新 PRD 取代）。
19. **敏感信息与私有区边界**：
    - **意图**：公开仓库任何个人信息/本机环境/密钥泄漏都全网可见且不可撤回；
      `private/` 一旦被设远端或打包，个人/机器信息同样外发。
    - 禁止在仓库跟踪目录（主仓库 + 私有子仓库提交内容）写入任何个人信息、本机
      环境信息、密码/密钥/凭据文件；确需保留只放不被版本管理的本地位置
      （`.gitignore` 忽略）或加密存储，绝不提交。
    - `private/` 禁设远端、禁打包（发布产物、zip、备份均不得包含）。
    - 例外：用户明确要求时，必须先做一次**全面个人信息检查（内容 + 全历史）→
      向用户报告 → 获用户确认**后方可执行。
    - **展示面**：发布链/打包自检输出与合规「红线遵循」项；**验收面**：内容级
      扫描门禁（`scan_secrets --strict`）+ 远端/打包断言 + 例外三连记录。

## 【通用】版本管理

- **版本号**：`version.json` 的 `version` 字段为单一事实来源，格式 `X.Y.Z.patchN`（第 4 段为
  字面 `patch` + 数字，从 0 开始）；git tag `vX.Y.Z.patchN` 与
  Release 使用同一版本。
- **递增规则**：版本号**从 `0.0.1.patch0` 开始**：
  - 补丁/小修复：默认只升第 4 段（`patchN` → `patchN+1`，如 `1.4.0.patch0` → `1.4.0.patch1`）；
  - 普通功能升级/补齐：升第 3 段并将第 4 段归零（`1.4.0.patch1` → `1.4.1.patch0`）；
  - 大功能升级：升第 2 段并将后两段归零（`1.4.1.patch0` → `1.5.0.patch0`）；
  - **前两位（major/minor）增加必须向用户确认**；破坏性变更必须用户确认并升
    major（首位）、说明迁移方案（`1.5.0.patch0` → `2.0.0.patch0`）。
  - bump 脚本：`python scripts/bump_version.py --part patchn|patch|minor|major`
    （默认 `patchn`，即最小单位）。
- **提交信息格式**：普通提交 `feat: / fix: / docs: / chore: / refactor: - 描述`
  （不带版本号）；**发布提交**（版本递增与发布前同步）带版本号
  `feat: vX.Y.Z.patchN - 描述`。
- **发布机制**：版本递增由 agent **本地**执行（`scripts/bump_version.py` 按
  `scripts/version-sync.json` 同步 `version.json` 与 `package.json` / `Cargo.toml` /
  `pyproject.toml` 等，同时更新 CHANGELOG——`private/` 不进 GitHub，CI 无法代劳）；
  推送 main 后，若当前 `version` 尚无对应 tag，CI（`.github/workflows/release.yml`）
  自动打 tag 并创建 GitHub Release。
- **手动/自动二选一**：手动发布（本地 bump + tag + `gh release create`）后不要再
  期望 CI 重复发布；CI 只发布「无 tag 的当前版本」，不会二次递增版本。
- **发布策略**：默认不自动发布（用户明确要求发布时才走发布流程）；如需自动发布，
  见 `private/AGENTS.md`「项目状态与版本」（初始化时可用 `--auto-release` 开启）；
自动发布视为用户对发布/推送的**预授权**（红线 3 的同意要求对常规发布视为已
  满足），但破坏性变更、永久删除等高风险操作仍须单独确认。
- **模板版本**：项目根 `version.json` 的 `template_version` 记录初始化/升级时的
  通用项目模板版本；
  升级见「模板升级」与 `docs/UPGRADE.md`。

## 【通用】模板升级（详见 `docs/UPGRADE.md`）

当通用项目模板发布新版本时：读模板仓库 `CHANGELOG.md`（版本变更历史）→ 比对项目
`version.json` 的 `template_version` → **只应用【通用】模块变更**（【项目专用】
内容绝不覆盖）→ 回读校验 → 更新 `template_version` → 记录到 CHANGELOG/STATUS。

## 【通用】发布流程（每次发布时执行；完整版见 `private/AGENTS.md`「发布流程」）

1. **版本递增**：`scripts/bump_version.py`（默认 patch；前两位须用户确认），随后
   agent 手工更新 `private/dev/CHANGELOG.md` 顶部（脚本只校验同步目标，不写
   CHANGELOG，防止覆盖人工编辑的发布说明）。
2. **文档就绪**：CHANGELOG / DESIGN / TEST-REPORT / STATUS / README / 根 AGENTS.md /
   private/AGENTS.md / 用户可见文档同步。
3. **同步 private 子 git（发布前必做）**：`scripts/pre_release_check.py` 一键完成
   （检查并自动提交 private 变动、版本一致性、泄漏扫描、ci_check 已实现等）。
4. **主仓库提交推送**：提交信息见「版本管理」；`git push`。
5. **打标签与 Release**：`git tag vX.Y.Z.patchN` + `git push origin vX.Y.Z.patchN` +
   `gh release create`（或推送 main 后由 CI 自动完成，手动/自动二选一）。
6. **分发/安装/部署**：按项目实际（安装包、zip、文档站点等）；**构建/打包产物统一
   输出到 `dist/`**（C 区生成物，不进 git，`.gitignore` 已忽略；`release.yml` 自动
   attach `dist/**`，产物在别处时同步调整 workflow）；**分发/打包前自测**：产物
   可运行、关键文件齐全、无密钥/配置/素材等运行时数据混入、**不含 `private/`
   内容（红线 19：禁打包）**。
7. **汇报**：汇总改动、版本、测试、Release 链接、安装位置与回退方式，附完成检查清单。

## 【通用】项目归档/退役（项目停止主动开发时执行）

- **触发**：项目停止主动开发（弃用 / 迁移 / 长期冻结）时，由**用户明确发起**归档；
  agent 不主动归档、不擅自删除。
- **归档流程**：
  1. **对齐与确认**：与用户确认归档原因与范围（只读冻结 / 迁移到新项目 / 删除），
     以及保留位置（本仓库 / 存档目录 / 归档仓库）；
  2. **最终发布**：按「发布流程」完成最后一次发版（版本递增、CHANGELOG /
     TEST-REPORT、审计、tag + Release），保证状态可复现；
  3. **归档标记**：README 顶部标注「⚠️ 已归档（只读）」+ 归档日期与原因；
     `private/AGENTS.md`「项目状态与版本」记录归档状态；
  4. **产物归档**：最终发布产物（`dist/**`）随 Release 保留；归档说明与最终快照
     放入 `archive/`（A 区，进 git，只读，见 `archive/ARCHIVE.md`）；如需本地存档
     再复制到项目外（不提交 git）；
  5. **经验沉淀**：把可复用经验写入 `EXPERIENCE-TO-TEMPLATE.md` /
     `EXPERIENCE-TO-KB.md`，并提醒用户真正沉淀；
  6. **收尾**：主仓库与 private 子 git 均提交干净；仓库/数据删除只由用户决定。
- **归档后约定**：只读维护（安全修复可走临时流程）；默认不再递增版本、不再自动
  发布（注意：`release.yml` 仍会对「尚无 tag 的新版本」自动发 Release，只读维护期
  不递增版本即可规避；如需机器级防呆可在 workflow 中据归档标记跳过）；重新激活时
  先更新 `private/AGENTS.md` 状态，并按「快速上手」重新 bootstrap。

## 【通用】测试与质量

- **检查命令**：`scripts/ci_check.py`（本地与 CI 共用入口；按项目实际实现
  lint / build / test）。
- **发布前必测**：运行检查命令 + 项目测试，结果记录于 `private/dev/TEST-REPORT.md`；
  **未通过不发布**。
- **测试素材**：本地测试库/测试项目放 `private/test/`（B 区）。
- **明文例外（仅此一种）**：本次改动不涉及运行时文件、且用户明确确认时，测试结论
  可沿用上一版本，必须在 TEST-REPORT 注明「用户确认沿用」；禁止 agent 自行省略。
