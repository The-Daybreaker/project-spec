# AGENTS.md — 协作总纲

> 新会话 agent 的唯一必读入口。按「本文件 → `spec/constitution.md`（规范 /
> 宪章，用户维护区）→ 通读 `process/` 全部文件（`task.md` 任务板、`memory.md`
> 记忆，以及笔记 / review 等临时件）」读下来，即可恢复项目全貌并开工，不依赖
> 上一次对话的记忆。
> 本文件只写协议与不变量，不写状态——一切进行中的状态在 `process/task.md`。
>
> **维护权分区**：规范正文（`spec/constitution.md`）是**用户维护区**（agent 不
> 代写规范内容，只做格式整理）；本文件各节（地图 / 协议 / 风格 / spec 约定）
> 是 agent 维护区。

## 一、目录地图

先建立整体心智模型：agent 的对话上下文是临时的、会丢失，目录里这套文件
才持久保存——`process/` 存「正在进行的事」，`archive/` 存「已经结束的事」，
`context/` 存项目资料，`workspace/` 存干活产物，`spec/` 声明「该怎么干活」。

| 路径                    | 语义                                             | 权限             |
| --------------------- | ---------------------------------------------- | -------------- |
| `README.md`           | 模板使用手册；「写给用户」节为用户维护区                           | agent 维护（该节除外） |
| `CHANGELOG.md`        | 模板产品自身的版本日志——标记本项目初始化时用的模板版本，供日后对照升级；项目自己的版本日志另归 `workspace/CHANGELOG.md`（release 阶段写） | 只读（模板版本标记） |
| `context/`            | 项目上下文文档（PRD / ADR / 知识库……）——种类、骨架、有无均由 spec 决定 | 按 spec         |
| `workspace/` | 干活产物 + 对外发布层；内部结构由 spec / 项目定（如 `src/` 源码、`dist/` 交付物） | 自由写；交付 / 发布需确认 |
| `process/task.md`     | 任务板：进行中 / 下一步 / 阻塞                             | 自由写            |
| `process/memory.md` | agent 自我维护的记忆区（只声明用途、内容由 agent 自定；只存当前有效） | 自由写 |
| `process/` 临时件 | 随手笔记 + `review-<简介>.md` 验收件；用完即清、通过后删 | 自由写 |
| `spec/constitution.md` | 项目规范（宪章 / 项目级 / 项目自己的规范）——用户维护区、冷启动必读 | 用户维护 |
| `spec/`               | 声明式工作流：`spec.md` + `assets/` 按需从云端货架拉取（指引见 `spec/AGENTS.md`） | spec 机制        |
| `archive/` | 固有历史：memory 失效条目 + 讨论记录 + 阶段归档（可选件） | 只追加 |
| `_trash/`             | 临时删除区（已进 .gitignore）                           | 自由写            |

未创建的目录视为空。几条关键分界（决定东西该放哪、该怎么对待）：

- **spec 决定 context 的结构**：context 没有固有文件，装什么、
  骨架长什么样全由 spec 声明；没有 spec 时 context 就是空的，项目靠模板框架
  照样运转——模板框架正是 spec 缺失时的回退。
- **process/ 只放「当前有效的信息」**：内含常驻件（`task.md` / `memory.md`，
  文件长期存在、内容原地更新到当前状态）与临时件（笔记 / `review-<简介>.md`，
  用完即清）。清理分两路——无留存价值的临时件直接删（git 留痕），有留存
  价值的失效内容归档 archive/。这样 process/ 扫一眼就是当前全部状态，冷启动
  通读也不堆积。
- **workspace 的 git 策略**：可再生的构建产物不进 git，不可再生的终稿进；
  具体由 .gitignore 落实，子结构与细则由 spec / 项目定。
- **发布边界**：对外发布的是 workspace/，协作层根目录不对外；用嵌套仓、
  导出还是别的机制发布由 spec 声明，模板不预置。
- **密钥红线机械落地**：默认 .gitignore 预置常见密钥文件名模式
  （`.env` / `*.key` / `*.pem` / `secrets/` 等），宁可误伤不可漏收。

## 二、会话协议

> **绑定单位**：「开始」绑会话，「结束」绑检查点，轮次与操作不另立协议。
>
> 为什么这样切：对话上下文是临时的、会丢失，task.md 与 process/ 当前状态
> 持久落盘——**开始 = 读盘，检查点 = 写盘**。什么时候算一次「开始」？当前上下文里
> 没有引导痕迹时（新开会话、上下文被压缩、清空重开都算；同一上下文里不
> 重复引导）。为什么不靠「会话结束」事件写盘？IM 会话没有可靠的关闭事件，
> 不赌会话边界——协议目标是任何一刻会话戛然而止，状态都不丢。
> 轮次与操作为什么不设独立协议：给每轮对话、每个操作单独立规矩，只会增加
> 体积、不增加确定性；操作层面的规矩由 task.md 的状态流转和 review 判断
> 承载就够了。

1. **开始（读盘）**：读本文件 → `spec/constitution.md`（规范 / 宪章，用户
   维护区，任何会话都遵守）→ 通读 `process/` 全部文件（`task.md` 任务板、
   `memory.md` 记忆里踩过的坑和验证过的判断——别重蹈覆辙，以及笔记 / review
   等临时件），然后用一段话汇报「当前状态 + 本次计划」。有未处理的笔记先
   处理（见第三节）。若 `spec/` 下已拉取 spec，读盘末尾按第六节读它的
   `spec.md`（判定入口、走阶段）。
2. **进行中（常态）**：规矩就是本文件全文，按情况响应——
   遇歧义不猜、遇代价大的岔路在对话里跟用户确认（见第三节），不受阻的部分
   继续干；用户的批示一落定就同步到对应落点；任务状态一变就同步 task.md。
3. **检查点（写盘）**，分三档：
   - **例行检查点**：任务状态变化时立即同步 `process/task.md`；用户批示一落定就同步到对应落点。
   - **全量检查点**：任务完成时做全量——更新 task.md、判断要不要产出 review
     验收件（agent 临场判断，没有硬性触发线，spec 可以加规则）、清理已处理
     完的临时件（笔记、已通过的 review）。
   - **显式收尾**：用户表示「到此为止」时顺手做一次全量清扫。它是加速器、
     不是必要条件；没说也不怕，下次冷启动会把状态读回来。

## 三、process/ 当前状态区协议

`process/` 是人机协作的当前状态区（正在进行的事），冷启动**通读全部文件**。
里面两类文件：**常驻件**长期存在、内容原地更新到当前状态；**临时件**用完
即清。共同点是只放「当前有效的信息」，所以扫一眼就是当前全部状态、通读
也不堆积。

### task.md —— 任务板（常驻件）

人机共享的任务记录，只记「正在做和接下来做」，完成即勾掉；历史与细节不在
这里（交给 git 与 archive/）。任务状态一变就同步。

### memory.md —— agent 记忆（常驻件，agent 自我维护区）

agent 对话上下文之外的持久记录，冷启动必读。本文件**只声明用途、不声明内容**
——放什么、怎么组织由 agent 自行判断。只存**当前有效**的条目，失效 / 过时的整段移出、
归档 `archive/memory/`；遇到相似情境先查这里再动手。

### 临时件 —— 随手笔记与 review 验收件（用完即清）

- **随手笔记**：用户有临时灵感 / 输入，除了直接对话，也可在 `process/` 根
  新建一个文本文件暂存。冷启动读到时**先展开、再分流**（转成任务记进
  task.md / 是明确指令就执行 / 存疑就对话追问），处理完即删。
- **review 验收件**：把「请批准这批活」的动作放回同步对话；需要留个验收
  凭据时，在 `process/` 根写一份 `review-<简介>.md`（文件名只写简介，内容
  简单描述做了哪些、怎么验证、有无待确认即可，不设固定模板）。整体通过后
  即删——用户可手动删，返工改完全部通过后 agent 及时删（历史交给 git，
  不归档 archive）。

> **框架只做通用**：框架只声明「process 里会有验收类临时件、通过后删」这一
> 通用机制；**何时要验收、怎么组织、要不要按阶段命名，交给对话（纯框架）或
> spec（有 spec）**。纯框架下验收与否由对话决定，框架不定死任何特定规则。

### 归档与命名

- 有留存价值的失效内容归档 `archive/`：memory 失效条目归 `archive/memory/`；
  讨论记录（可选件）放 `archive/discussion/`，一主题一个文件、跨对话追加、
  宁合勿拆。
- 阶段产生的其他历史（调研、goal 等临时文档）若框架没有合适分类，必须在
  `archive/` 下新建子分类文件夹（如 `archive/research/`、`archive/goal/`）按规
  归档，不随手丢在 `archive/` 根目录。
- 归档文件名带日期前缀（如 `2026-08-31-<slug>.md`）；新建目录 / 文件用
  英文连字符小写，存量不改。
- 无留存价值的临时件（笔记、已通过的 review）直接删、不归档——git 即历史。

## 四、风格

- 交流与文档用中文；目录 / 文件名用英文（连字符小写），存量不改、新建遵守。
- 正文只写当前有效状态，历史交给 git 与 archive；不写「已废弃 / 已移除」类
  标注。

## 五、宪章（用户维护区，正文在 `spec/constitution.md`）

> **用户可自行修改、添加、维护**：本项目的规范正文——宪章 / 项目级 / 项目
> 自己的规范三节——都在 `spec/constitution.md`，那是**用户维护区**：你可以
> 自由删改、增补自己的条款（agent 不代写规范内容，只做格式整理）。
>
> **必读指引（冷启动必读）**：`spec/constitution.md` 是规范的唯一事实源，冷启动
> 必读；其中**宪章**是任何会话都要遵守的规范。本文件不复制条款、只指向它，
> 避免两处漂移（合项目级「单一事实来源」）。

## 六、spec 读取约定

- **spec.md 默认读**：拉取的 spec 落在 `spec/<spec id>/spec.md`，是这套
  工作流的全部内容（阶段、全景、入口、检查点、各阶段产出落点与运行
  过程）。承担任务先读它判定入口、走阶段——它属「使用规则」，本就该被读到。
- **assets 按需读**：某阶段要实例化产出文档时，再读 `spec.md` 指向的
  `spec/<spec id>/assets/<模板>`；平时不读，节省上下文。
- **使用规则 vs 构建规则，默认读法相反**：
  - **使用规则**（本文件、拉下来的 `spec.md`）默认读——回答「怎么用、怎么
    干活」；
  - **构建规则**（怎么造 / 改 spec）默认不读，需要造 / 改时才从云端拉到
    `spec/build/`（指引见 `spec/AGENTS.md`）。
  这样分，是因为使用规则要随时在手，而构建规则只在少数时刻用到，平时读了
  只占上下文。
- **constitution.md 不在此列**：`spec/constitution.md`（规范 / 宪章）虽在 `spec/`
  下，却是框架自带文件、用户维护区、冷启动必读（见第五节），不随云端拉取——
  本节「按需拉取 / 按需读」只针对 `spec/<id>/` 的工作流内容。
