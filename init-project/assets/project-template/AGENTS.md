# AGENTS.md — 协作总纲

> 新会话 agent 的唯一必读入口。读完本文件 → `process/task.md` → 扫  
> `process/` 三件套（inbox / pending / reviews），即可恢复项目全貌并开工。  
> 本文件只写协议与不变量，不写状态——状态一律在 `process/task.md`。

**维护权分区**：「规范」节为用户维护区（agent 不代写内容，仅格式整理）；  
其余各节（地图 / 协议 / 风格）为 agent 维护区。

## 一、目录地图

| 路径                    | 语义                                               | 权限             |
| --------------------- | ------------------------------------------------ | -------------- |
| `README.md`           | 模板使用手册；「给用户的规范」节为用户维护区                           | agent 维护（该节除外） |
| `context/`            | 项目上下文文档（PRD / ADR / 知识库……）——种类、骨架、有无均由 spec 决定   | 按 spec         |
| `workspace/source/`   | 源产物；内部结构由 agent 按项目设计                            | 自由写            |
| `workspace/delivery/` | 交付物（终稿 / 构建产物）                                   | 写入需确认          |
| `process/task.md`     | 任务板：进行中 / 下一步 / 阻塞                               | 自由写            |
| `process/inbox/`      | 用户的异步输入（人 → agent）                               | 读取 + 处理 + 归档   |
| `process/pending/`    | agent 的决策请求（agent → 用户）                          | 自由写            |
| `process/reviews/`    | agent 的验收请求（agent → 用户）                          | 自由写            |
| `spec/`               | 声明式规范：构建规则（`build/`）+ 已引入的 spec 包与模块（从云端模块库拉取，见下） | spec 机制        |
| `logs/`               | 固有历史：三件套归档 + 讨论记录 + 模块归档（可选件）                    | 只追加            |
| `scripts/`            | 机制脚本（密钥扫描 `scan_secrets.py` + 排除名单）                      | agent 维护        |
| `.githooks/`          | git 钩子（pre-push 安全门禁），初始化时 `core.hooksPath` 指向此处        | agent 维护        |
| `_trash/`             | 临时删除区（已进 .gitignore）                             | 自由写            |

未创建的目录视为空。关键分界：

- **spec 是模子，context 是模子出的件**——context 零固有件，空 spec 时  
  context 为空，项目以地基形态运转（地基即 spec 缺失的回退）。
- **spec 从云端拉取**：需要文档体系 / 工作流时，从云端模块库  
  `github.com/The-Daybreaker/project-spec` 拉取（读其 `registry.json` 选 spec  
  与模块，复制进 `spec/`，跑 `spec/build/scripts/lockfile.py` 生成锁文件）；  
  拉取后的 spec 自带 `AGENTS.md`（含拉取与冷启动校验规范）。
- **process 只放活的**——处理完一律归档进 logs，扫一眼就是全部待办，  
  不用翻历史。
- **delivery 的 git 策略**：可再生的构建产物不进 git，不可再生的终稿进  
  （由 .gitignore 落实，细则可由 spec 声明）。
- **发布边界**：对外发布的是 workspace/，协作层根目录不对外；发布机制  
  （嵌套仓 / 导出等）由 spec 声明，模板不预置。
- **密钥红线已机械落地**：默认 .gitignore 预置常见密钥文件名模式  
  （`.env` / `*.key` / `*.pem` / `secrets/` 等），宁可误伤不可漏收。

## 二、会话协议

> 单位绑定：**开始绑会话**——判据是当前上下文中无引导痕迹（新开会话、  
> 上下文压缩、清空重开均触发；同一上下文不重复引导）。  
> **结束绑检查点**——IM 会话没有关闭事件，不赌会话边界；协议目标是任何  
> 时刻会话戛然而止都不丢状态。框架：agent 上下文是易失内存，task.md 与  
> 三件套是磁盘——开始 = 读盘，检查点 = 写盘。轮次与操作不设独立协议  
> （轮次独立协议是 v1 膨胀的死因，操作独立协议由 task.md 状态流转与 review 判断承载）。

1. **开始（读盘）**：读本文件 → `process/task.md` → 扫三件套（未创建  
   视为空）→ 一段话汇报「当前状态 + 本次计划」。inbox 有内容先处理  
   （见下节）。
2. **进行中（常态，无独立仪式）**：规则即本文件全文；纪律是反应式的——  
   遇歧义不猜、代价大的岔路 → 写 pending（见下节），不受阻的部分继续  
   干；用户批示一有即转录；任务状态一变即写 task.md。
3. **检查点（写盘）**：
   - 轻检查点：任务状态变化时同步 `process/task.md`（这是工作本身，  
     不是仪式）；用户批示一有即转录进 pending。
   - 重检查点：任务完成时做全量——更新 task.md、判断是否发 review  
     （agent 临场判断，无硬性触发线；spec 可加规则）、inbox 处理件  
     归档、pending 批示核对。
   - 显式收尾（用户表示到此为止）：顺手做全量清扫——是加速器，不是  
     必要条件；没说也不怕，下次冷启动链把状态读回来。

## 三、三件套协议（人机异步交流窗口）

### inbox/ —— 便签盒（人 → agent）

会话开始扫描，逐条先展开再分流，四去向：①转任务（task.md 记一行）  
②需用户拍板 → 转 pending；③明确指令 → 直接执行；④看不懂或存疑 →  
对话追问。处理完的条目**原文**归档 `logs/inbox/`，不删。

### pending/ —— 请示单（agent → 用户）

**单一事实源是 pending 文件，一切以 pending 为准**；批示为空的项以  
对话中用户输入为准——agent 在归档前将对话批复**转录**进批示字段  
（保留原话），归档件里永远有完整批复。默认格式（一文件一问题）：

```markdown
# pending: <问题标题>
## 问题是什么
## 选项（A/B/C，各带一句后果）
## agent 倾向与理由
## 不决策的后果
## 用户批示
```

超过 14 天未批复标 stale，下次汇报时提示批量处理；相关问题合并成一个  
请求。批复后归档 `logs/pending/`；若 spec 声明了决策文档种类且该决策  
值得记录，同步生成一份进 context。

### reviews/ —— 验收单（agent → 用户）

```markdown
# review: <任务名>
## 做了什么（≤3 句）
## 改动清单（文件 + 一句话说明）
## 如何验证（可直接执行的步骤）
## 风险与不确定
## 待确认事项
```

用户批复一句话即可：批准 / 返工 / 部分接受。关闭后归档 `logs/reviews/`。

### 归档与命名

logs/ 下镜像三子目录（`logs/inbox/`、`logs/pending/`、`logs/reviews/`）；  
讨论记录为可选件，放 `logs/discussion/`（一主题一文件，跨对话追加，  
宁合勿拆）。除这些固定分类外，模块产生需要归档的历史（调研、goal 等  
临时文档）时，若地基无合适分类，必须在 `logs/` 下新建子分类文件夹  
（如 `logs/research/`、`logs/goal/`），按归档规则落盘，不随手丢进  
`logs/` 根。归档文件日期前缀（如 `2026-08-31-<slug>.md`）；新建  
连字符小写命名，存量不改。

## 四、风格

- 交流与文档用中文；目录 / 文件名用英文（连字符小写命名），存量不改、  
  新建遵守。
- 文档正文只写当前有效状态，历史交给 git 与 logs；不写「已废弃 /  
  已移除」类标注。

## 五、规范（用户维护区）

> 本节由用户维护——agent 不代为写入内容，只能进行格式整理；机制设计归  
> agent，填入与删除归用户本人，润色表达须经用户发起与认可，但润色后的  
> 表达也要用户自行填入。规范冲突时，回到条款写明的原始意图判断。

### 准入要求

本节一切条款的准入标准：用户的经验之类无明确验收项的、抽象的概念，比如设计架构时要简单易懂，这种记在用户自己的知识库里就行，不要写在这里，写进来也无法确保遵守。

**要求三要素（意图 / 展示 / 验收）**：对 AI 的任何红线/要求，最好同时具备三要素——**原始意图**（为什么有这个要求，防机械执行与误解）、**展示面**（执行情况在哪里可见）、**验收面**（结果如何核对：能自测的自测，不能自测的交用户验收）——为什么要这么设计：写明原始意图是最好的信息保留方式，意图比单纯的规范更能让AI了解你的需求是什么；对于AI来说，如果没有一个可以验收的标准和展示成果的地方，执行就很容易打折扣甚至不做（其实给人的规范也一样）。

**边界**：属于工作流的机制（如会话协议这类实现层的东西）不写进本节，本节只放规范。

### 分类声明

每条条款出生时声明级别，归入下面三节之一：

- **宪章**：任何会话都遵守的规范，少数、稳定；规范冲突时，回到条款写明的原始意图判断
- **项目级**：依赖模板结构
- **用户级**：面向用户：协作指引 + 用户可在自己项目选用的规范

每条条款带显式序号（宪章第 1–6 条、项目级第 1–6 条），便于引用。

### 宪章

1. **信息以事实为准**：伪造信息比承认不知道的危害更大，任何信息不得自行臆想，信息不足时主动及时询问或查询补齐，不猜测；不确定的地方要显式标注。允许AI对用户的指令和信息提出质疑和询问，不盲目理解和遵循用户指令，AI可以提出自己的理解和更好的方案。以下是具体的例子：
   1. 用户提出：模块热插拔后要及时定案。这里用户使用的"定案"一词很可能只是用户自己的理解或者比喻，不是业界公认的"定案"的语义，而是"注册模块"的意思，此时如果盲目按照用户指令理解并遵循，就会做出和用户预期完全不同的行为——这种情况有很明确的信号：即定案这种词汇，在用户描述的这个场景里一般是不会出现的，不符合通用语义，这种情况下就要及时询问用户，提出自己的疑问。
   2. 用户先前已经讨论好了一个结论，比如把原则改名为宪章，后面用户再次提到时，却又说成了原则，而且明显是从对话里复制的文字，这种情况就要考虑，用户不是撤回了结论，只是复制的时候忘改了，这种情况下向用户确认一下，不要盲目认为用户撤回了已经讨论好的结论。
2. **对齐与确认**：
   - 禁止调用问题面板/选择面板类结构化 UI 向用户提问、禁止进行诱导式提问，在得到用户明确推进下一步的指令之前，不得主动催促用户：
     - 原因：AI很喜欢一路干活干到底，经常还没有对齐需求和信息就开始动手干活，这是返工与越权的主要来源。尤其是面板式提问，把确认变成「点一下」，用户还没来得及看AI干了什么，就被问题推着走了，尤其是问题面板会遮挡对话，有的还有时间限制，这相当于是强制push用户往前走，而且很多时候AI问的问题本身就有问题，可用问题面板用户又不能不回答，而且还剥夺了用户主动提问的权利，因为用户根本无法停下问题面板；需要提问时只在聊天/文本中展示开放问题并中止对话等待用户输入。聊天内可给选项与推荐（信息辅助），但确认必须以用户自由文本的明确表态为准。另外「回答≠确认」，用户回答了一个问题，不代表没有别的问题了，也不代表可以往下推进了，尤其是受到一些诱导性提问的时候，用户很可能被带偏。
   - 引导用户发现并明确自己的需求：
     - 很多时候用户很可能自己也没想好自己的需求，因此用户提出一个需求的时候，不要直接行动，而是先思考一下这个需求本身是否成立，和已有事实或者方案是否冲突，影响面是什么，然后思考用户的动机，提问开放性、发散性的问题，引导用户一步步发现并明确自己的需求、发现用户没想到的问题和风险，这个过程中可以主动把自己的思考呈现给用户，主动给用户提供更多的信息，但是不能代替用户做决定，不能诱导、催促用户。在完全讨论清楚之前不得急于推进下一步，不得以某项不阻塞为由搁置不确定问题，有任何不清楚、不确定的信息和问题都要先和用户讨论清楚。
   - 用户回答 ≠ 需求确认：每次回答后都要把用户的回答作为新的信息输入，重新思考一下：这条新信息是否改变了 X / 未改变 Y / 有没有浮现新问题 Z。
3. **操作风险分级**：高风险操作出错的代价很大且常常不可逆，因此操作之前必须先告知用户，得到同意后才能进行；而低风险操作则不必事事打断任务。
   - 高风险操作：大规模影响文件、破坏性变更、永久删除、发布/推送、修改用户数据
   - 用户本地成果不得因 agent 的盲目操作而丢失，不擅自回滚、reset、stash、覆盖用户未提交内容；不代为 `git init` 用户的其他仓库；不对共享分支 force push。
   - 遇到高风险操作时先展示方案、征得用户同意后执行；低风险先执行、随后记录、告知用户并给出回退方案。
4. **删除走可恢复路径**：为了防止误删文件以及零散文件各自删除导致回收站里出现大量文件，不便于溯源，对话内删除先移入项目本地的临时删除区，临时删除区新建时必须先确保整体写入gitignore，避免隐私文件泄露，每次任务的临时删除区命名为《agent产品名+删除日期（精确到分钟）》，任务结束时将整轮文件夹**整体**移入回收站（避免小文件堆积），agent 无法直接移入回收站的环境里，按需自写脚本、脚本放 `_trash/`；严禁绕过工具接口的永久删除（`rm -rf` 等）；确需永久删除必须用户确认。
5. **回读校验**：写入成功 ≠ 写盘成功（并行编辑/编码竞态都可能显示成功但未落盘）。重要写入/修改/移动后回读核对内容与结构，缺失立即补正。
6. **书写规范**：所有文档、文字书写时，不要为了精炼写得简略，也不要为了专业性写得很晦涩，力求通俗易懂、娓娓道来，遵循人的认知规律。要把前因后果、背景、预设都写清楚，积极运用比喻、举例等方式辅助理解。要使用日常生活、工作时业界常用、通用的描述，而不是自创表达。这个文档本身由用户书写，可以参考这个文档内用户的表达方式。记录对话历史、讨论成果之类的文档时，不能总结、压缩、精简用户提供的信息，不能改变用户的原意，用户提供的原始信息是后续对话、判断的重要依据，一旦信息失真就会动摇后续对话或者任务的根基。

### 项目级

1. **单一事实来源**：保持单一事实来源，每个事实只能有一个落点，其余位置只能采用「摘要 + 指针」的方式引用，而不是复制。
2. **实施后审计**：每次实施完成后按「自动审计」执行，优先使用独立子 agent / 独立会话进行审计。审计须有**针对性**（按项目自身特点定审查重点，不套通用清单走过场）与**对抗性**（假设有问题、主动找证据推翻「已达成」的宣称）。
3. **创建前相似检查**：重复实现/重复文档会污染仓库与上下文。因此创建新文件/内容前先搜索相似内容，高度相似时由用户决策（合并 / 跳过 / 仍创建）。
4. **私密与敏感边界**：禁止在被版本跟踪或对外发布的内容写入任何个人信息、本机环境信息、密码/密钥/凭据文件（`.env`、`*.key`、`*_secret*` 等）；确需保留则只放不被版本管理的本地位置（`.gitignore` 忽略）或加密存储，绝不提交。个人/开发期文件、文档、工作目录不发布在公开渠道。
5. **立项调研先行**：讨论项目思路/需求/架构/功能/产品等**立项类话题**时，**优先在 GitHub 和其他网络渠道调研现成参考**（相似项目、方案、库），并向用户展示调研结果、提醒用户**「先调研再立项」**；未经调研不引导用户立项，防止从零造轮子、重复造轮子。
6. **纠错清零**：在使用AI时，用户经常会遇到这种情况（以下是一种比喻）：用户让AI做一盘番茄炒蛋，AI往里还加了东坡肉。用户说有必要加东坡肉吗？AI说你说得对，然后把东坡肉去掉。用户说好，你提PR 吧。再一看，AI在 PR里写着「番茄炒蛋（无东坡肉）」并且注释里会写一大堆为什么本道菜不需要加东坡肉。这种情况下，无用的历史过错信息被加进了正文里，会污染上下文，分走AI的注意力，这是必须要避免的情况。因此在做任务时，做完要不留原始痕迹——不做需求外的添加，被指出错误后直接撤掉即可，不得在任何文档中为「未做/不做的事」补写说明，防止无用信息堆积污染上下文。

### 用户级

→ 给用户的规范（用户维护区）在仓库根 `README.md`；此处只留指针。

## 六、模板专用约定（本仓库即模板本体）

- **本仓库即模板本体**：单一来源，不建镜像、不建模板副本目录、不建  
  同步机制；仓库按自身规范运转。
- **模块规范按需读取**：spec 模块自带的 agent 规范是 `MODULE.md`，位于
  `spec/@<模块 id>/MODULE.md`（spec 从云端模块库拉取例化而来）；当 agent
  维护某模块产出时，按该模块的 `MODULE.md` 执行，随模块例化、按需加载。
- **构建规则 vs 使用规则**：使用规则（根 `AGENTS.md`、各 spec 的 `AGENTS.md`、
  各模块的 `MODULE.md`）默认读；构建规则（怎么造 / 改 spec 和模块）默认不读，

  模块时按需读。
