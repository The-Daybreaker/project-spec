# build — 构建规则（怎么写一份 spec.md）

> 本目录随模板出厂，是「构建规则」层：回答「一份 spec.md 长什么样、怎么写、怎么组织阶段与 assets」。**默认不读**——日常执行任务（判定入口、走阶段）读的是「使用规则」（项目根 `AGENTS.md`、各份 `spec.md`）；只有「设计或修改 spec」时才读本目录。

## 一、构建规则 vs 使用规则

一套项目里有两类规则，性质相反，别混：

| | 构建规则 | 使用规则 |
| --- | --- | --- |
| 回答什么 | 怎么**写** spec.md | 怎么**用** spec.md |
| 读者 | 设计 / 修改 spec 的人或 agent | 日常执行任务的人或 agent |
| 默认读不读 | **默认不读**（只在造 / 改时读） | **默认要读**（每次任务都读） |
| 落点 | 本目录 `spec/build/`（随模板出厂） | 项目根 `AGENTS.md`、各份 `spec.md` |
| 命名 | 非 `AGENTS.md`（避免被各软件自动扫描误读） | `AGENTS.md` / `spec.md`（本就该被读到） |

一句话：**构建规则是「说明书怎么写」，使用规则是「说明怎么用」**。

## 二、一份 spec 长什么样

```
spec/<spec-id>/               ← 项目里一份 spec 的结构
├── spec.md                   ← 主干：这套工作流的全部内容
└── assets/                   ← 各阶段产出文档的参考骨架（按需，部分阶段没有）

preset-spec/<spec-id>/        ← 回流到公开仓最佳实践集时，另带一份 CHANGELOG.md
├── spec.md
├── assets/
└── CHANGELOG.md              ← 最佳实践集的版本变更日志（项目本地不需要）

spec/build/                   ← 本目录：构建规则
├── build.md                  ← 本文件
└── spec-template/spec.md     ← spec.md 骨架母版（照它写新 spec）
```

`spec.md` 内部结构（照 `spec-template/spec.md` 母版写）：

1. **头部**：标题 +「使用场景」+「版本」两行引述（项目本地自写自用的 spec 可不写版本）；
2. **一、这套工作流**：场景一句话 + 阶段链 + 横切说明；
3. **二、概览**：mermaid 全景图 + 入口表（流程调节：不同大小任务启用哪些阶段）+ 控制权分段与检查点；
4. **三、各阶段**：每个阶段一个小节，统一三段式——产出（落点 + assets 引用） / 运行过程 / 规范边界。

## 三、写 spec.md 的几条规则

- **一份文档自包含**：一个 spec 的全部内容都在这一份 spec.md（+ assets），不拆成模块。阶段之间的先后衔接画在 §二的 mermaid 全景图里，不靠跨文件声明；箭头是推荐顺序、并不强制，可按实际情况调整。
- **阶段三段式**：每个阶段只写「产出落点 / 运行过程 / 规范边界」三样，不写「输入」（输入由全景图箭头表达）、不重复描述（一处说清即可）；运行过程分步骤时用有序列表（1. 2. 3.），一步一行、不用内联编号。
- **只写模型拿不到、容易出错的信息**：产出骨架这类格式参考拆进 `assets/`，spec.md 主体保持精炼、用于导航（渐进式披露），显而易见的话不重复写。
- **入口 = 流程调节**：一套 spec 定义多个入口，不同等级的任务从不同入口进、启用不同阶段子集——简单的事不走重流程、复杂的事不漏环节。入口用 markdown 表写在 §二（集合、不表顺序），执行顺序参考全景图。
- **检查点按控制权设**：协作产出段（与用户反复讨论，天然处处确认）不设显式检查点；显式检查点只设在控制权交接处（如「实施放行」「收口放行」）。
- **产出落点沿用框架目录**：阶段产出落在模板框架的既有目录（`context/` 放上下文文档、`workspace/` 放干活产物与交付物（内部结构如 `src/`、`dist/` 由 spec 定）、`process/` 放当前状态、`archive/` 放归档），spec.md 只声明哪个阶段往哪落。

## 四、版本号与 CHANGELOG（只对回流最佳实践集的 spec）

- **版本号（SemVer）**：贡献到公开仓 `preset-spec/` 的 spec，版本写在 `spec.md` 顶部，格式 `主.次.修订`（如 `0.1.0`）——主版本不兼容变更才 +1、次版本向后兼容新增 +1、修订号向后兼容修复 +1；主版本为 0 是开发期，不做兼容承诺。
- **CHANGELOG**：最佳实践集里的每份 spec 带 `CHANGELOG.md`，按版本记录变更（分类参考 Keep a Changelog：Added / Changed / Removed / Fixed），跨版本升级先读它。
- **项目本地的 spec 不背版本号**：spec 拉进或写进项目后归项目自由改，本地以 git 为历史；版本与 CHANGELOG 只是最佳实践集标「这是哪一版」、供日后对照升级用。本目录（构建规则）自身也不带版本，随模板整体版本走。

## 五、新建一个 spec

1. 把本目录 `spec-template/` 复制成 `spec/<新 id>/`（要回流贡献到最佳实践集，则复制到公开仓 `preset-spec/<新 id>/`）；
2. 把母版里的 `<占位符>` 换成实际内容：按头部 / §一 / §二 / §三 的顺序写 `spec.md`，按需增删阶段小节；
3. 按需补 `assets/` 产出骨架；回流最佳实践集的另填 `CHANGELOG.md`。

## 六、本目录内容

```
spec/build/
  build.md                ← 本文件
  spec-template/
    └── spec.md           ← spec.md 骨架母版（照它写新 spec）
```
