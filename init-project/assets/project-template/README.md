# 通用项目模板 · 使用手册

欢迎，这个项目是用 **project-spec（面向「人 + AI 助手协作」的通用项目模板）** 初始化出来的。本文件面向**你——项目的主人**，帮你快速看懂手里这套目录、以及日常怎么和 AI 助手配合。AI 助手遵循的完整协议在根 `AGENTS.md`（单一事实源），本文件是它面向人的精简辅助手册。

## 这个项目是怎么组织的

先建立一个最重要的心智模型：**根目录是「协作层」，`workspace/` 是「发布层」**。

- 根目录这一圈文件和目录（`AGENTS.md`、`process/`、`context/`、`spec/`、 `archive/`、本文件），是你和 AI 助手交流用的「协作中枢」：任务进展、 AI 记忆、需求方案、行为规范都在这里，被 git 跟踪、随时可回溯， **默认不对外发布**。
- 真正的干活产物（代码、成品、对外交付物）放在 `workspace/`，**对外发布的是它**。用嵌套的独立 git 仓还是导出打包，由你选用的工作流（spec）声明。

这样设计的好处是：开发过程的一切讨论和状态都有完整版本痕迹，而公开出去的发布物干干净净，不带过程文件。

另一个关键模型：**AI 的对话上下文是临时的、会丢失，目录里的文件才持久保存**。对话可以随时关，只要状态落在文件里，下次任何 AI 助手「读盘」就能接上。

## 这个项目怎么运转：读盘 → 干活 → 写盘

AI 助手每次新会话开工，都会按固定顺序**冷启动（读盘）**：

1. 根 `AGENTS.md`——协作总纲：目录地图、会话协议，以及 §五 规范（你维护的行为规范，冷启动必读）；
2. `process/` 下全部文件——任务板 `task.md`（进行中 / 下一步 / 阻塞）、 `memory.md`（AI 记忆）、以及笔记 / review 等临时件；
3. 如果项目装了工作流 spec，再读 `spec/<id>/spec.md`，判断这次任务从哪个入口进、走哪些阶段。

读完它会先用一段话向你汇报「当前状态 + 本次计划」，然后再动手。干活过程中，**任务状态一变就写回 `process/task.md`**（写盘）——不赌对话正常关闭，任何一刻会话中断，状态都不丢。

你日常只需要做三件事：开工前对齐需求、过程中看任务板掌握进展、收尾时确认结果。

### 几个高频场景

| 场景 | 你要做什么 |
| --- | --- |
| 新开一轮对话 | 等 AI 冷启动汇报，确认它理解的当前状态无误即可 |
| 布置新任务 | 直接说需求；需求较复杂时，先和它讨论清楚再让它动手（宪章要求先对齐） |
| 想知道进展 | 看 `process/task.md`，「进行中」节头一两行就是当前状态 |
| 准备关闭对话 | 提醒 AI 更新任务板（见下方「写给用户」第 4 条），确保下次无缝衔接 |
| 换一个 AI 工具接手 | 无需交代背景，让它先读根 `AGENTS.md` 冷启动即可 |
| 找历史结论 | 当前有效的决策、方案在 `context/`；被取代的旧内容与过程记录在 `archive/`；更细的历史查 git |

## 按需设计工作流（spec）

框架本身不含任何具体工作流，保证项目「什么都不配也能转」。当你需要一套成体系的流程时（例如软件开发的「愿景 → 方案 → 需求 → 开发 → 测试 → 审计 → 发布」），**以自己设计为主**，可参考公开仓 `preset-spec/` 最佳实践集（模板与最佳实践集同仓，就在 `github.com/The-Daybreaker/project-spec` 的 `preset-spec/` 目录）。

设计 spec 推荐按「还原场景 → 场景拆流程 → 流程抽象为 spec」的方法论推进：

1. **还原场景**：和 AI 助手一起把项目的典型工作场景讲清楚（谁、做什么、产出什么、有什么约束）；
2. **场景拆流程**：把场景拆成阶段链（推荐推进顺序 + 横切阶段），设几档入口（流程调节）；
3. **流程抽象为 spec**：把公开仓 `preset-spec/build/` 构建规则复制到 `spec/build/`，按 `build.md` 和 `spec-template/` 母版写成 `spec.md`，按需补 `assets/` 产出骨架。

如果最佳实践集里有场景相近的现成 spec，也可以直接复制一份进项目自由改——浏览 `preset-spec/specs/` 选定 → 把 `spec.md` + `assets/` 复制进本项目的 `spec/<id>/` → 按项目情况修改。拉下来的 spec 归你所有，本地演进由 git 记录，最佳实践集不做锁定和漂移校验。

完整机制说明见本项目 `spec/AGENTS.md`。

## 目录速览

| 路径 | 放什么 |
| --- | --- |
| `AGENTS.md` | 协作总纲，AI 助手的唯一必读入口：目录地图、读盘/写盘协议、process 规则、spec 读取约定；§五 是你维护的行为规范 |
| `README.md` | 本文件，面向人的使用手册；其中「写给用户」一节由你维护 |
| `CHANGELOG.md` | **模板自身**的版本标记（本项目初始化自哪版模板，供日后对照）；你项目自己的版本日志日后写在 `workspace/CHANGELOG.md` |
| `spec/AGENTS.md` | spec 机制说明书：spec 是什么、怎么设计与获取、怎么读 |
| `spec/<id>/` | 工作流（`spec.md` + `assets/`），自己设计或参考最佳实践集；没装时不存在 |
| `context/` | 项目上下文文档（愿景 / 方案 / PRD / 决策记录等），装什么、骨架由 spec 决定；没有 spec 时为空 |
| `process/` | 协作当前状态区：常驻的 `task.md` 任务板、`memory.md` AI 记忆，以及笔记 / `review-*.md` 验收件等临时件（用完即清） |
| `workspace/` | 干活主工作区 + 对外发布层；内部结构（如 `src/` 源码、`dist/` 交付物）由 spec / 项目定 |
| `archive/` | 有留存价值的历史归档（只追加）：失效记忆、讨论记录、阶段归档 |
| `_trash/` | 对话内删除的暂存区（已进 .gitignore，不入库），任务结束后整体清入系统回收站 |

## 写给用户

> 由于现有Agent的能力不足，很多规范写进AGENTS.md也无法保证执行，因此这里写一些面向用户的提醒，由用户来把关。

1. **使用正向提示词**：除非是在给AI设定规范，否则最好不要使用“不要xxx”这样的提示词，因为从现有大模型的表现来看，越是强调不要，模型越会记住，并且会把“不要xxx”直接写进文档内，污染上下文。因此最好采用正向描述，“把xxx改为xxx”、“只需要xxx”。
2. **信息安全**：在项目发布到公开渠道之前，最好让Agent审计一下项目内是否有隐私文件，AI总是会把各种信息写进文档、代码内部，为了防止信息泄露，最好也人工复核一下各个文档。
3. **压缩重读：** 在触发上下文压缩后，很可能丢失上下文原有的规范要求等信息，因此在发现触发上下文压缩后，请及时提醒AI重读AGENTS.md，也可以在agent内设置钩子。
4. **对话关闭落盘:** 虽然模板中规定AI及时更新task，但是很难保证绝对遵循，因此在决定关闭一个对话时，请提醒AI更新task并确保冷启动无缝衔接。

## 两份核心文件的分工

| 文件 | 面向谁 | 谁维护 | 内容 |
| --- | --- | --- | --- |
| `AGENTS.md` | AI 助手（人也可读） | agent 按机制维护，§五 规范除外 | 协作协议与不变量：目录地图、会话协议、spec 读取约定；§五 是行为规范（宪章 / 项目级 / 项目自定义，你可自由删改增补） |
| `README.md`（本文件） | 人 | agent 维护，「写给用户」节除外 | 面向人的使用手册：怎么用好这套结构 |

协议条款有疑问时，以根 `AGENTS.md` 为单一事实源；想调整 AI 的行为规矩，改 `AGENTS.md` §五。
