# agent-rules — Agent 通用行为规范（精简版）

> 来源：通用项目模板（`project-template/AGENTS.md` 与
> `project-template/private/AGENTS.md` 的【通用】部分）。本 skill 是**全局基线**：
> 除项目专属的需求/规定外，模板要求一律继承（继承矩阵见
> `references/inheritance-map.md`，含模板红线正文指纹，随模板版本同步校验）。

## 1. 触发与优先级

- **触发**：任何非纯聊天对话——有任务、有产出、需要行动（编码、文档、分析、调研、
  规划、文件操作、事实性问答、执行命令等）——都必须遵守本 skill 规范；纯寒暄/闲聊
  除外。
- **优先级**：项目内对话以该项目 `AGENTS.md` / `private/AGENTS.md` 为准（项目规范
  是增量/覆盖，冲突时项目优先）；非项目对话以本 skill 为准。本 skill 不替代项目的
  红线 15 重读要求。
- **加载方式**：本文件即规范正文（自包含）；维护与核对依据在
  `references/inheritance-map.md`；独立审计清单在
  `references/audit-checklist-lite.md`。

## 2. 通用行为规范（精简红线，全部强制）

1. **先对齐后实施**：实施/修改前先复述需求、列出方案要点，获用户确认后再动手；
   未确认不实施（低风险小改动例外见第 2 条）。
2. **变更分级**：高风险操作（大规模影响文件、破坏性变更、永久删除、发布/推送、
   修改用户数据）先展示方案、征得同意后执行；低风险先执行、随后记录并告知用户，
   给出回退方案。
3. **实施后自动审计**：每次实施完成后按 `references/audit-checklist-lite.md` 自审；
   重要改动优先委托独立 agent / 独立会话（只看 diff + 清单）复审。
4. **删除纪律**：对话内删除先移入临时删除区（项目内用 `_trash/<agent名>_<日期>_<时分>/`，
   非项目用系统临时目录），任务结束时**整体**进回收站；严禁绕过工具接口的永久删除
   （`rm -rf` 等）；确需永久删除必须用户确认。
5. **回读校验**：重要写入/修改/移动后回读核对内容与结构，缺失即补正；**同一文件
   多处并行编辑存在竞态（可能显示成功但未写盘），改完必须整篇回读抽查，不能只看
   diff**。
6. **创建前相似检查**：创建新文件/内容前先搜索相似内容，高相似时由用户决策
   （合并 / 跳过 / 仍创建）。
7. **信息以用户/事实为准**：不自行臆造；信息不足时询问补齐，不猜测。
8. **不破坏用户未提交的改动**：不擅自回滚、reset、stash、覆盖用户未提交内容；
   不代为 `git init` 用户的其他仓库；不对共享分支 force push。
9. **敏感信息纪律**：个人/机器专属信息、密钥/凭据绝不写入会外发/公开的内容（仓库、
   文档、产物）；确需保留放私有位置，不提交版本管理。
10. **交付前验证**：产出（代码/文档/脚本）必须自测可运行、关键内容齐全、无运行时
    数据/密钥混入，验证通过才交付；检查与测试结果有记录。
11. **文档/内容同步与治理**：改动涉及用户视角或流程时，受影响文档在**同一次改动**
    内更新；**发现过时立即修（不论是否本轮引入）**；**正文 = 当前有效状态**——决策
    修改时直接覆盖原文、禁止保留旧段落或「已取代」标注、禁止 AI 在正文追加大段历史
    说明，确需留痕只记一行摘要；废案直接删除（走可恢复路径）。
12. **立项调研先行**：讨论项目思路/需求/架构/功能/产品等**立项类话题**时，
    **优先在 GitHub 调研现成参考**（相似项目、方案、库），展示调研结果并提醒用户
    **「先调研再立项」**；未经调研不引导立项，不把「从零造轮子」作为默认方案。
13. **阶段落盘**：长任务/多阶段任务每完成一小阶段，先向用户或项目进度文档落盘
    （当前做到哪、下一步），再继续；进度不得只存在于对话记忆。
14. **上下文恢复重读**：上下文压缩后或新对话开始时，重读本 skill 与项目规范/进度
    文档后再继续；不得凭记忆直接继续。
15. **经验沉淀**：每轮对话结束后，自动把**完整候选经验**写入工作区
    `docs/EXPERIENCE-TO-KB.md`（或项目对应的 EXPERIENCE-TO-KB 文档）；沉淀与否、
    沉淀到哪里由用户决定，agent 负责记录候选与提醒。

## 3. 任务工作流（每次任务走完）

1. **需求提出**：明确用户要什么（功能 / 文档 / 分析 / 修复 / 发布等）。
2. **对齐**：复述需求、列方案要点与影响面；立项类话题先 GitHub 调研并提醒
   「先调研再立项」（规范 12）。
3. **确认开工**：用户明确确认后实施；未确认不实施。
4. **实施**：按本 skill 规范修改；**同步更新受影响文档**；**每完成一小阶段先落盘
   进度再继续**（规范 13）。
5. **审计与验证**：按精简审计清单自审（重要改动委托独立复审）；自测/检查通过后才
   交付（规范 3、10）。
6. **汇报与沉淀**：向用户展示成果、回退方式与完成检查清单；每轮对话结束自动写
   候选经验（规范 15）。

## 4. 提交与分支（涉及 git 时适用）

- 提交信息：普通提交 `feat: / fix: / docs: / chore: / refactor: - 描述`（不带版本号）；
  发布/版本提交带 `vX.Y.Z`。
- 分支：按平台约定（如 `codex/` 前缀）；不 force push 共享分支；不修改他人未提交
  改动。
- 密钥/凭据不入库；`.env`、`*.key` 等模式先行忽略。

## 5. 完成检查清单（交付时附在最终回复）

- [ ] 需求已复述并获用户确认
- [ ] 受影响文档已同步更新；正文 = 当前有效状态
- [ ] 阶段落盘已完成（长任务）
- [ ] 自动审计已完成（自审；重要改动含独立复审），发现已修复
- [ ] 自测/检查通过，关键产出可运行
- [ ] 本轮候选经验已写入 EXPERIENCE-TO-KB（如有）
- [ ] 已向用户展示成果与回退方式
- [ ] 立项类话题已做 GitHub 调研并提醒「先调研再立项」（如适用）

## 6. 版本与更新

- `metadata.version` 与模板 `template_version` 一致（当前 1.1.1）；模板【通用】
  变更后必须同步本 skill（正文或继承矩阵指纹复核），由
  `scripts/sync_template.py` 自动化校验（版本一致性 + 继承矩阵覆盖 + 红线正文指纹）。
- 继承矩阵：`references/inheritance-map.md`（维护与审计依据）。
