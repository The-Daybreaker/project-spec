# RFC-0002 — 红线与要求可验证性改造：实施方案（方案文档）

> 已采纳/已否决：已采纳（D1-D7 全部按推荐）
> 关联：PRD-0002（已定稿）、RESEARCH-0002、RESEARCH-0003
> 位置说明：本工作区（母项目）无 `private/dev` 登记册，RFC 落于 `docs/`；

## 背景与目标

按 PRD-0002 落地八项需求（F1-F8）。本方案文档给出实施层面的决策点、候选对比、
推荐方案、影响面与风险；评审通过后记录架构决策（ADR-0002）并吸收进设计文档。

## 决策点与候选对比

### D1 辩护性措辞扫描的载体

- 候选 A：独立脚本 `scripts/scan_defensive.py`（推荐）——职责单一，可独立挂进
  检查命令与发布链；提交信息/PR 命中硬拦、注释/文档命中输出人工复核清单；
- 候选 B：并入 `scan_secrets.py`——省一个文件，但职责混杂（凭据 vs 措辞），
  降噪规则互相干扰；
- 候选 C：仅审计清单人工检查——无法机器验证，违背三要素。

### D2 推送前钩子扫描范围

- 候选 A：全量跟踪文件 `--strict`（推荐）——实现简单、覆盖完整；典型项目扫描
  秒级，可接受；
- 候选 B：只扫待推送提交的 diff——更快，但需解析推送范围，复杂且易漏（历史
  已有内容不拦）。

### D3 精简版规范对红线 19 的处理

- 候选 A：更新精简版规范 9「敏感信息纪律」吸收红线 19 扩展内容（推荐）——
  精简版保持 18 条（规范 1 新增三要素，原 1-17 顺延为 2-18，9 吸收 19），
  继承矩阵指纹更新；
- 候选 B：精简版新增规范 19——条目与模板 1:1，但精简版失去「合并」意义。

### D4 合规「红线遵循」的展示形式

- 候选 A：阶段卡合规两行扩为七项，增加「红线遵循（本阶段相关已展示）」（推荐）
  ——改动最小、与现有合规块同构；
- 候选 B：独立「红线遵循」区块——更醒目但增加阶段卡体积。

### D5 路线图校验强度

- 候选 A：`check_dev_docs.py` 断言（版本列表与需求索引/version.json 对齐、
  需求文档关联字段引用存在、定稿需求必登记路线图条目）（推荐）——机器可验，
  满足三要素验收面；
- 候选 B：仅文档约定——无法验证，违背三要素。

### D6 共识卡锚点格式

- 候选 A：状态快照内固定块「📌 共识卡」含四个二级标题（认知基线/缺口/质疑/
  推进结论）+ 「重检：」行，`check_dev_docs.py` 按锚点解析断言（推荐）——
  可机器校验、与阶段卡单一真相一致；
- 候选 B：自由文本——不可校验。

### D7 存量规范三要素体检的修复方式（用户定）

- 候选 A：本轮全修（所有缺口一次补齐，随本模块发版）；
- 候选 B：出符合性矩阵 + 缺口清单，按优先级分批（缺口修复独立发版）。

## 推荐方案总览

### F1/F2 红线重编号、三要素与体检

- 模板根 AGENTS.md「通用红线」：新增红线 1「要求三要素（意图/展示/验收）」
  （自指，按三要素写）；原 1-17 顺延为 2-18；新增红线 19「敏感信息与私有区
  边界」；每条红线正文按「意图 / 展示面 / 验收面」三段式补全；
- 全局引用校准：grep 新旧编号清单（根/私有 AGENTS、阶段定义、流程、审计清单、
  ADR-0001「红线 17」→ 18、技能摘要「红线条数 17 条」→ 19、继承矩阵指纹、
  工作区文档）；审计清单「红线条数硬事实」同步；
- 三要素体检：产出符合性矩阵（模板全部红线 + 精简版规范 + 工作区自身规范，
  每条一行意图/展示面/验收面/缺口）→ 缺口清单与优先级 → 修复方式按 D7 用户定；
- 精简版规范：规范 1 新增三要素，原 1-17 → 2-18，规范 9 吸收红线 19（D3-A）。

### F3 推送前安全门禁（三层）

- 模板层：`scan_secrets.py` 复制进 `project-template/scripts/`（保持 stdlib-only，
  自排除逻辑保留）；`pre_release_check.py` 增加内容级扫描步骤（调用
  `scan_secrets.py --strict`，高危或个人信息命中即门禁失败）；
- 本地推送层：模板新增 `.githooks/pre-push`（调用 `python scripts/scan_secrets.py
  --strict`，失败退出 1 阻止推送）；`init_project.py` 初始化时执行
  `git config core.hooksPath .githooks`（Windows/POSIX 通用）；母项目同步启用；
- 持续集成层：`ci.yml` 增加 `python scripts/scan_secrets.py --strict` 步骤
  （不扫历史，fetch-depth 默认；兜底非主防线）；
- 冒烟自检：`smoke_init.py` 扩展——新项目初始化后注入样例文件，验证 pre-push
  钩子确实拦截。

### F4 红线 19 与私有区防外发

- 红线 19 正文（意图/展示面/验收面）：跟踪目录禁个人信息/本机环境/密码/密钥
  文件；`private/` 禁设远端、禁打包；例外三连（全面检查→报告→确认）；
- `pre_release_check.py` 增加断言：`git -C private remote -v` 为空、主仓库跟踪
  文件不含 `private/`、发布产物（`dist/**` 及打包清单）不含 `private/`；
- 发布流程「分发/打包前自测」补「不含 private/」检查项；
- 审计清单同步检查项。

### F5 测试模块

- `PHASES.md`：审计验证阶段验证节点（13）拆子阶段——测试设计（用例清单）→
  自测执行 → 用户验收 → 结论入测试报告；
- `TEST-REPORT.md` 骨架双区化：自测区（编号/场景/步骤与数据/预期/实际/结果）+
  用户验收区（编号/场景/预期/负责人/签署标准，对齐 UAT/IEEE 829）；
- `TESTING.md` 扩展：用例登记表 + UAT 要素说明 + 示例代码块（标注「示例，
  框架/依赖由项目自选」；模板不预置 `tests/`）；
- `ci_check.py` 注释示例更新（接入项目测试入口的示范）。

### F6 红线 17（原 16）细化与辩护性措辞扫描

- 红线 17 正文改写：意图（番茄炒蛋/东坡肉比喻）+ 展示面（交付展示 diff 影响
  文件清单、合规项）+ 验收面（审计检查 + 措辞扫描 + 用户核对 diff）；
- 新增 `scripts/scan_defensive.py`（D1-A）：扫描提交信息（`git log`）与 PR 描述
  （命中硬拦）＋注释/文档（跟踪文件内容，命中输出人工复核清单）；第一版规则
  （`已移除|已删除|已去掉|不再需要|不需要|不适用|未引入|暂不实现|为什么不需要|
  为什么没有|多余` 及「X（无 Y）」型结构）；
- 挂接：`ci_check.py` 调用（提交信息硬拦）+ `pre_release_check.py` 集成；
- 审计清单同步检查项。

### F7 共识卡与反定型强化

- 红线 18（原 17）正文更新：硬触发清单（需求方向调整/调研结论形成/定稿/采纳/
  放行前/验收标准变更/发现需求矛盾/范围变更 → 必须展示共识卡）；重检行外部化
  （每次回答后一行「重检：新信息改变 X / 未改变 Y / 浮现 Z」）；
- `PHASES.md` §5：反定型条件块 → **共识卡固定块**（4 项：认知基线/缺口/质疑/
  推进结论 + 用户逐项表态）；合规两行六项 → 七项（加「红线遵循」）；
- `FLOW.md`：P1 子流程与需求引导状态机更新（回答重检 → 重检行；反定型展示 →
  共识卡）；
- `check_dev_docs.py` 增加断言：决策型节点状态快照含「📌 共识卡」块且四节非空、
  含「重检：」行（D6-A）；
- 审计清单同步。

## 风险与缓解

- 重编号漏改引用 → 全局 grep 新旧编号清单 + 审计「红线条数硬事实」断言；
- 辩护性措辞误报 → 双档（提交信息硬拦、注释/文档人工复核）+ 规则可配置白名单；
- 钩子不生效（Windows/用户未配）→ 初始化脚本配置 `core.hooksPath` + 冒烟自检
  注入样例 + 发布链与 CI 兜底（三层互补）；
- 路线图与登记册漂移 → `check_dev_docs.py` 断言；
- 体检缺口过多导致范围膨胀 → D7 由用户定修复方式（全修/分批）。
