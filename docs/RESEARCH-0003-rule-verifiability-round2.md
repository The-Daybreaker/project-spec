## 背景与问题

PRD-0002 增补 F8（长期需求与展望文档分层）后，用户要求对本轮需求再做一轮调研，
覆盖第一轮未深挖的四个主题：

1. 需求文档分层（愿景 → 路线图 → 版本需求）的业界实践；
2. 测试模块与用户验收（UAT）文档实践；
3. 反定型/共识卡对应的决策防偏实践（premortem 等）；
4. 「红线可验证」对应的可执行规范（policy-as-code）思路。

## 发现记录

### 发现 1：需求分层是标准结构——愿景 → 路线图 → 版本/发布 → 需求（2026-08-27）

- FAA Agile Program Management、Aha! 等资料一致：**产品愿景**定义长期目的与
  非功能方向；**产品路线图**按战略优先级描述演进计划；**版本/发布**是「何时」；
  **功能/需求**是「什么」。PRD 模板按层级选择（product/release/epic/feature）。
- GitLab、Atlassian：路线图必须作为**单一事实来源**并持续更新（honest &
  strategic），否则失去信任。
- **结论**：F8 双层结构（长期路线图 + 版本需求文档）与业界标准一致；路线图
  必须「正文=当前状态、覆盖式更新」，与模板文档治理一致。

### 发现 2：用户验收测试（UAT）文档要素明确（2026-08-27）

- BugHerd / BrowserStack / 教学资料：UAT 模板应含——测试用例编号、场景/步骤/
  数据、预期结果、负责人、工具、**签署（sign-off）标准**、缺陷上报方式。
- IEEE 829 测试文档体系：测试用例规格（编号/输入/预期）、测试日志（谁跑、
  顺序、通过与否）、测试报告。
- **结论**：F5 测试报告「用户验收区」按这些要素落地：用例编号 / 场景 / 预期 /
  负责人 / 签署标准；自测区用例编号 + 预期 + 实际 + 结果。

### 发现 3：反定型/共识卡对应成熟的决策防偏实践（2026-08-27）

- **Premortem**（Gary Klein / Kahneman & Klein）：设想「这个决定已经失败」，
  反推失败原因——与反定型「反例/替代解释」同构，且被证实可降低过度自信。
- WRAP 决策框架：对抗确认偏误/狭隘框架/过度自信——含「prepare to be wrong」
  （premortem、预案、检查点）。UXcel：靠**结构性护栏**（检查清单、premortem、
  显式信心等级、过程与结果分离），而不是「更努力保持客观」。
- **结论**：F7 共识卡的「质疑（反例+替代解释）」「推进结论」与 premortem/
  信心等级实践一致；可选的增强是推进结论附「信心等级/残余风险」。

### 发现 4：「红线可验证」对应可执行规范（policy-as-code）（2026-08-27）

- 政策即代码：把规则写成**可执行、可版本化、可验证**的产物，而不是手工清单
  （inferensys / Mondoo / emergentmind）。
- arXiv「Executable Governance for AI」：用 LLM 把自然语言政策编译为可运行
  **检查清单与场景规则**，记录来源/范围/例外/严重度/可测试性，人工可跑。
- **结论**：三要素的「验收面」优先做到**可执行检查**（扫描门禁、断言、冒烟），
  不能可执行化的给**人工核对清单**——这正是 PRD-0002 F1/F3 的思路，有外部
  依据；模板「自研 stdlib 扫描器 + 审计清单」即轻量版政策即代码。

## 结论与建议

1. F8 双层需求结构与业界一致，路线图定位为**单一长期事实来源**（私有、
   覆盖式更新），版本需求文档只写增量；
2. F5 测试报告双区按 UAT/IEEE 要素补全（编号/场景/预期/负责人/签署）；
3. F7 共识卡与 premortem 同构；可选增强「推进结论附信心等级/残余风险」；
4. F1 三要素的验收面明确为「可执行检查优先，人工核对清单兜底」（政策即代码
   思路的轻量落地）。
