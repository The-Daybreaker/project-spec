# PRD-0001 — agent 提问与共识确认机制重设计（模板【通用】）

> 状态：已实现 | 优先级：P1 | 创建：2026-08-26 | 定稿：2026-08-27 | 实现版本：1.4.1.patch0 | Supersedes：—
> 位置说明：本工作区（母项目）无 `private/dev` 登记册，PRD 落于 `docs/`；
> 模板骨架（`project-template/private/dev/prd/`）保持不动。

## 背景与目标

**背景**：现有 agent 需求收集普遍采用「问题面板/选择题 → 用户作答 → agent 推进」模式，
存在结构性缺陷：

1. **回答 ≠ 确认**：用户回答某个问题 ≠ 确认整体需求；agent 常把「回答」当「确认」，
   把自设的问题切面当需求本身；
2. **面板诱导**：选择题面板暗示答案、点选快于思考，用户被 agent 节奏推着走，等发现
   偏离时已晚；
3. **约束过软**：现有「P1 需求引导：先复述意图、提开放问题」缺乏机制级强制，无法
   约束模型行为；
4. **无共识载体**：agent 不检查自己的默认假设、共识缺口、方案隐含前提；「确认」
   没有显式、可撤销的载体。

**目标**：在模板【通用】层建立「提问与共识确认机制」：

- 红线：严格禁止问题面板（选择面板类结构化 UI）向用户提问；
- 回答 = 新信息输入（非事实终点），agent 每次回答后内部重检问题空间；
- 共识快照 + 显式确认：每次推进前展示已达成的共识清单，用户逐项表态；
- 反定型 6 项：关键/风险节点完整展示；每次提问后内部思考；
- 确认不锁定：任何新信息可回到该流程；PRD 定稿后走变更流程；
- 覆盖所有提问/确认节点（P1-P5 决策型确认 + agent-rules 非项目对话）。

## 用户与场景

- 用户：使用通用项目模板的项目中与 agent 协作的人（开发者/需求方）。
- 场景：
  - P1 需求引导（倾听意图 → 引导提问 → 澄清 → 确认需求 → 调研 → 需求明确）；
  - P2 方案/RFC=技术方案文档/ADR=架构决策记录/原型/DESIGN=设计文档确认；
  - P3 确认开工；
  - P5 发布确认；
  - 任何 agent 需要向用户提问/获取确认的时刻（含 agent-rules 精简版覆盖的非项目对话）。

## 需求范围

### 功能需求

- **F1 面板红线（强制）**：禁止调用「问题面板/选择面板」类结构化选择 UI 向用户提问
  （含 `request_user_input` / AskUserQuestionTool 类工具）；提问仅在聊天/文本中呈现，
  并中止对话等待用户自由输入。
- **F2 选项边界**：聊天内可给出选项与推荐（信息辅助），但**不得仅依赖选择项就盲目
  向下推进**；确认必须以用户自由文本的明确表态为准；禁止「列 3 个选项请选择」式
  提问作为确认手段。
- **F3 回答≠终点**：每次用户回答后，agent 将回答作为新信息输入，内部重检问题空间
  ——哪些问题因答案失效、哪些新问题浮现、哪些假设被推翻/加强；不要求每次展示，
  但必须执行。
- **F4 反定型 6 项（关键/风险节点展示）**：当前理解 / 我的假设 / 尚未确认事项 /
  反例 / 替代解释 / 重新审视问题。触发时机：需求理解确认、PRD/RFC/ADR 评审、
  开工确认等关键决策节点，或 agent 检测到高风险/不确定时；平时每次提问后内部思考。
- **F5 共识快照 + 显式确认**：每次推进前展示「已达成的共识清单」（逐项），用户逐项
  表态（自由文本）；推进以共识确认为准，**不以「回答了问题」为准**。
- **F6 共识达成条件**：完整展示反定型（关键节点）+ 用户明确确认 = 达成共识；过程中
  agent 不得 push 流程、不得诱导（禁止「回答即可继续」「默认你同意」类表述）。
- **F7 确认不锁定**：任何新信息出现允许回到上述流程重新审视；PRD 定稿后的变更走
  **变更流程**（变更流程在 P2 方案中定义：触发/审批/记录）。
- **F8 覆盖范围**：所有提问/确认节点（P1-P5 全部决策型确认 + agent-rules 非项目对话）。

### 非功能需求

- **N1 落点**：模板【通用】——根 AGENTS.md 红线 + `private/AGENTS.md` +
  `private/dev/PHASES.md` + `docs/FLOW.md` + `docs/audit-checklist.md`；skills——
  `agent-rules` 精简版（含继承矩阵指纹）+ `init-project` 资产镜像 +
  `references/init-steps.md` 覆盖；所有项目受益。
- **N2 展示克制**：反定型不每次展示，避免形式主义与对话臃肿（借鉴问题预算：
  一次 1-3 个开放问题）。
- **N3 可审计**：行为规则进入 audit-checklist / audit-checklist-lite 对应检查项。

## 验收标准

1. 模板根 AGENTS.md「通用红线」新增面板红线（F1/F2）与确认机制（F5/F6）条目；
   `private/AGENTS.md` 开发规范同步。
2. `PHASES.md`「需求引导方法论」与 `docs/FLOW.md` §3.1 需求引导状态机更新（含共识
   快照、反定型、回答重检、变更流程回退）。
3. `agent-rules` SKILL.md 精简版继承新红线（继承矩阵指纹更新）；audit-checklist-lite
   同步。
4. `init-project` 资产镜像同步 + `sync_template.py` 全链绿（版本一致性/指纹/覆盖/
   副本）。
5. `quick_validate` ×2 绿；六处副本重装验证（发版时）。
6. 行为可测：需求讨论中不使用问题面板；用户回答后不自动推进、先展示共识快照；
   关键节点展示反定型；用户确认后才推进。

## 不在范围

- 不重设计 P1-P5 阶段体系本身（保留串行与决策型/执行型分类）；
- 不改版本号体系；
- 不定义具体平台 UI 实现（只约束 agent 行为）；
- 不处理模型层的技术实现（纯规范/文档层面）。

## 调研结论

红线 13 调研已完成（详见 `docs/RESEARCH-0001-agent-questioning.md`）。摘要：主流
框架默认用选择题面板收集需求，但面板的疲劳/诱导副作用有广泛讨论；业界已有「总结+
最终确认」（SpecBench）、「假设显式化」（discover）、「显式确认后推进」（clarify-first /
Tessl）等散点实践，但**未见**把「禁面板 + 开放提问 + 回答重检 + 共识快照 + 反定型 +
变更流程回退」组合成模板级红线的现成方案——本需求属组合创新。

## 风险与开放问题

- 变更流程的具体形态（触发/审批/记录位置）——P2 方案细化；
- 共识快照与现有阶段卡的呈现整合——P2 方案；
- 「所有确认节点」的清单枚举——P2 完善；
- 反定型展示与「不 push」的边界（避免展示本身变成形式主义）。
