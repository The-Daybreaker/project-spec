# PRD-0002 — 红线与要求可验证性改造（三要素元规范 + 安全门禁 + 测试模块 + 反定型强化）

> 状态：已定稿 | 优先级：P1 | 创建：2026-08-27 | 定稿：2026-08-27 | 实现版本：— |
> Supersedes：— | 关联：RESEARCH-0002、ADR-0001（红线编号联动）、ADR-0002（待建）
> 位置说明：本工作区（母项目）无 `private/dev` 登记册，PRD 落于 `docs/`；
> 模板骨架（`project-template/private/dev/prd/`）保持不动。

## 背景与目标

**背景**：实测与经验表明，对 AI 的约束存在结构性失效：

1. **不可展示、不可验收的要求，AI 倾向不做**：红线 16（范围克制与纠错清零）与
   反定型均「无法验证、无法确认是否被遵守」；问题不在规则文字，而在规则没有
   「展示面」与「验收面」，也没有解释原始意图（例：番茄炒蛋/东坡肉）；
2. **推送前个人信息校验只有内容扫描器**：`scan_secrets.py` 仅存在于母项目工作区，
   未接 git 推送门禁、未进模板；持续集成在推送之后才跑，对密钥泄漏「太晚」；
3. **测试不是模块**：测试只有指引与报告骨架，无流程位置、无「自测/用户验收」
   分流，测试用例由项目自己实现；
4. **私有区防外发缺口**：`private/` 可被设远端或打包，个人/机器信息存在外发路径；
5. **反定型约束力弱**：关键/风险节点定义模糊（有裁量空间）、反定型为条件块
   （平时不出现、不留档）、内部思考不可监督、合规清单不含反定型。
6. **需求文档无长期规划载体**：现有需求文档按需求/版本各一文件（PRD-XXXX），
   无「长期需求 + 展望 + 排期」文档；新对话/恢复时需读多份历史需求文档才能
   了解全局，阅读负担重。

**目标**：在模板【通用】层建立「红线与要求可验证性」体系：

- 新增**红线 1「要求三要素（意图/展示/验收）」**作为最顶层红线，存量红线整体
  顺延重编号，并按三要素**全面体检**存量规范/红线；
- 新增**红线 19「敏感信息与私有区边界」**：跟踪目录禁个人信息/本机环境/密码/
  密钥文件；`private/` 禁设远端、禁打包；例外须全面个人信息检查→报告→用户确认；
- 推送前安全门禁**三层全做**（本地推送钩子 + 发布链 + 持续集成兜底）；
- 测试模块正式入流程（测试设计→自测→用户验收），测试报告双区化；
- 红线 17（原 16）细化并补齐三要素（含番茄炒蛋/东坡肉原始意图）；
- 反定型强化：硬触发清单 + 重检行外部化 + 共识卡（内容级融合反定型 6 项为
  4 项）固定块 + 合规「红线遵循」展示 + 脚本锚点留档。
- 需求文档分层：新增**长期需求与展望文档**（唯一长期入口）+ 版本需求文档
  （本版本增量），实现「每版本只看长期文档 + 本版本文档」。

## 用户与场景

- 用户：使用通用项目模板的项目中与 agent 协作的人、母项目维护者、agent 执行者。
- 场景：
  - P1 需求引导：用户提出新红线/要求时，按三要素转化（意图/展示/验收）后方可定稿；
  - P3/P4 实施与验证：推送前钩子拦截、测试报告双区、共识卡留档、辩护性措辞扫描；
  - P5 交付发布：发布链内容级扫描门禁、交付汇报附「红线遵循核对表」；
  - 非项目对话：agent-rules 精简版同步继承三要素与共识卡/重检行。

## 需求范围

### F1 新红线 1「要求三要素（意图/展示/验收）」（最顶层）

- 任何对 AI 的红线/要求必须同时具备：**原始意图**（为什么有这个要求）、
  **展示面**（执行情况在哪里可见）、**验收面**（结果如何核对）；缺任一要素
  不得定稿；
- 验收面**优先可执行检查**（扫描门禁/断言/冒烟，政策即代码思路的轻量落地），
  不能可执行化的给**人工核对清单**；
- 能自测的自测（脚本断言/扫描门禁/文档一致性），不能自测的交用户验收；
- 红线 1 自身按三要素写（自指示范）；
- 全链重编号：原 1-17 → 2-18，新增 19；全局 grep 校准所有引用（根/私有 AGENTS、
  阶段定义、流程、审计清单、ADR-0001、精简版规范、继承矩阵、技能摘要、审计清单
  「红线条数硬事实」）。

### F2 存量规范/红线三要素体检

- 产出「三要素符合性矩阵」：覆盖模板全部红线 + 精简版规范 + 工作区自身规范，
  每条一行（意图 / 展示面 / 验收面 / 缺口）；
- 产出缺口清单与修复优先级，经用户确认后实施（本轮全修或分批发版，用户定）。

### F3 推送前安全门禁（三层全做）

- `scan_secrets.py` 进模板 `scripts/`；
- `pre_release_check.py` 集成内容级扫描（高危硬拦、个人信息 `--strict` 门禁）；
- 模板新增 `.githooks/pre-push`，`init_project.py` 初始化时配置
  `core.hooksPath=.githooks`；母项目同步启用；
- `ci.yml` 增加扫描步骤（兜底，非主防线）；
- 注入样例测试钩子确实拦截（冒烟自检覆盖）。

### F4 新红线 19「敏感信息与私有区边界」

- 禁止在仓库跟踪目录（主仓库 + 私有子仓库提交内容）写入任何个人信息、本机
  环境信息、密码/密钥/凭据文件；确需保留只放不被版本管理的本地位置或加密存储；
- `private/` 禁设远端、禁打包；发布链/打包自检断言（远端检查 + 产物不含
  `private/`）；
- 例外流程：用户明确要求时，先做**全面个人信息检查 → 向用户报告 → 获确认**
  后方可执行。

### F5 测试模块入流程

- 审计验证阶段内正式定义「测试模块」子阶段：测试设计（用例清单）→ 自测执行 →
  用户验收 → 结论入测试报告；
- `TEST-REPORT.md` 双区化：**自测区**（agent 可执行的命令/用例/结果）与
  **用户验收区**（不能自测、需人判断的条目，交付时逐项表态）；
  - 用例要素：编号 / 场景 / 步骤与数据 / 预期结果 / 负责人（agent 或用户）/
    实际结果 / 签署标准（对齐 UAT 与 IEEE 829 实践）；
- `TESTING.md` 扩展：用例编写规范 + 用例登记表；`tests/` 骨架示例（标注为示例，
  框架/依赖由项目自选，模板脚本保持零依赖）；
- `ci_check.py` 示例更新（接入测试入口的示范）。

### F6 红线 17（原 16）范围克制与纠错清零细化

- 正文补原始意图（番茄炒蛋/东坡肉比喻：不加菜、撤菜不留疤）；
- 展示面：交付时展示 diff 影响文件清单；合规「红线遵循」项；
- 验收面：审计清单检查项 + **辩护性措辞扫描**（提交信息/PR 描述命中硬拦、
  注释/文档命中人工复核清单）+ 用户核对 diff；
- 辩护性措辞第一版规则：`已移除|已删除|已去掉|不再需要|不需要|不适用|未引入|
  暂不实现|为什么不需要|为什么没有|多余` 及「X（无 Y）」型结构。

### F7 反定型强化（共识卡内容级融合）

- **硬触发清单**（消除裁量）：需求方向调整、调研结论形成、定稿/采纳/放行前、
  验收标准变更、发现需求矛盾、范围变更 → 必须完整展示共识卡；
- **重检行外部化**：每次用户回答后输出一行「重检：新信息改变 X / 未改变 Y /
  浮现 Z」（日常非关键节点仅此一行）；
- **共识卡固定块**（决策型推进前，替代原反定型条件块 + 共识快照）：
  ① 认知基线（当前理解 + 假设 + 已确认共识）② 缺口（尚未确认 + 新浮现问题）
  ③ 质疑（反例 + 替代解释）④ 推进结论（重新审视 + 本次需用户逐项表态项）；
- 阶段卡合规两行从六项扩为**七项**，增加「红线遵循（本阶段相关红线已展示）」；
- 落地校验：`check_dev_docs.py` / 审计清单断言「决策型节点状态快照含共识卡且
  各项非空 + 重检行存在」；内容质量由人工审计；
- 交付汇报（任务收尾/发版）附**红线遵循核对表**（全表，每条一行展示锚点 +
  验收结果）；发版必附。
- 评审记录：可选增强「推进结论附信心等级/残余风险」——**不采纳**（2026-08-27
  用户定稿确认）。

### F8 长期需求与展望文档（需求文档分层改造）

- 模板新增 `private/dev/ROADMAP.md`（长期需求与展望 + 版本排期）作为**唯一长期
  入口**，初始化即存在（骨架，随模板同步）：
  - 文件名 `ROADMAP.md`，文档标题「长期需求与展望（路线图）」（私有区）；
  - 愿景与长期目标（当前有效，覆盖式更新，正文=当前状态）；
  - 需求地图：长期条目 ↔ 版本 ↔ 需求文档引用（每版本一行：已发布/进行中/规划）；
  - 版本排期：已发布版本、当前版本、规划版本（含粗略范围）；
  - 文档治理：历史由 git 承担；确需留痕仅变更日志一行；
- 版本需求文档（PRD-XXXX）保持冻结留史，头部新增「所属版本」「关联路线图条目」
  字段；只写本版本增量，不重复长期内容；
- 加载规则/文档映射更新：新对话/恢复时按「长期文档 + 本版本文档」读取；
  阶段定义 §3 阶段↔文档映射、文档职责划分、加载规则表同步；
- 校验：`check_dev_docs.py` 增加路线图一致性断言（版本列表与需求索引/
  version.json 对齐、需求文档关联字段引用存在、定稿需求必登记路线图条目）；
- 工作区（母项目）同步落地 `docs/ROADMAP.md`（登记 PRD-0001/0002 与 1.4.x
  版本排期）。

## 验收标准

### 能自测（agent 执行，进测试报告自测区）

- A1：模板与精简版红线条数 = 19，红线 1 三要素齐全；全局 grep 无旧编号残留
  （红线条数硬事实同步）；
- A2：三要素符合性矩阵覆盖全部存量红线/规范，缺口清单含优先级；
- A3：`scan_secrets.py --history --strict` 全绿；新项目初始化后 pre-push 钩子
  生效，注入样例被拦截；`pre_release_check` 集成扫描通过；持续集成绿；
- A4：打包/远端断言拦截 `private/` 外发（注入样例）；
- A5：辩护性措辞扫描：提交信息/PR 硬拦样例命中、注释/文档人工复核清单正确输出；
- A6：决策型节点状态快照断言共识卡存在且各项非空、重检行存在；
- A7：冒烟自检（`smoke_init.py`）全绿，含钩子与测试模块骨架检查。
- A8：路线图骨架随模板初始化存在；`check_dev_docs.py` 断言通过（版本列表与
  需求索引/version.json 一致、需求文档关联字段引用存在）；需求文档定稿必登记
  路线图条目；冒烟自检覆盖「每版本只读两份」路径。

### 不能自测（交用户验收，进测试报告用户验收区）

- U1：体检缺口清单的修复范围与优先级确认；
- U2：红线 17 番茄炒蛋示例与 diff 展示的观感核对；
- U3：共识卡 4 项结构在真实一轮流程中的可读性/是否真被执行；
- U4：例外流程走查（全面检查→报告→确认）符合预期；
- U5：新项目初始化后测试模块文档/骨架对实际项目的可用性（用例与框架由项目
  自行落地）。
- U6：实际体验「路线图 + 本版本需求文档」的阅读路径，确认满足「不用读太多
  文档」。

## 不在范围

- 不重写模板其余部分；PRD-0001 已实现机制仅做编号/融合调整；
- 不引入第三方依赖（gitleaks 等仅文档推荐为可选增强）；模板脚本保持零依赖；
- 不替项目选择测试框架、不写项目级测试用例；
- 不执行历史提交重写、不执行知识库沉淀（由用户决定）；
- 已安装六处副本不在本模块直接重装（随发版流程统一重装校验）。

  分批发版则相应调整）。
