## 四、发现详述

### P1-1 远端公开仓库仍暴露重写前的泄露历史（安全处置收尾未完成）

- **证据链**：本地 main=`c978b71`（重写后）vs 远端 main=`b0a4c70`（该 SHA
  本地对象库不存在，`cat-file -e` = NO → 属重写前历史）；本地 tag
  `v1.4.2.patch0`=`d9d5abf` vs 远端=`cdd6c26`（同样本地缺失）；远端最后推送时间
  `2026-08-27T08:38Z`（重写前）；STATUS 记录「推送待网络恢复」，本轮实测
  `ls-remote` / `gh api` 均成功 → **网络已恢复**。
- **影响**：安全处置的目的是公开面零泄露；强推未执行前，旧历史（含本机路径/
  用户名残留）在 GitHub 上任何人可克隆可见。此为「本地绿 ≠ 公开面绿」的典型。
- **遏制条件**：forks=0（无扩散副本）；Release 无资产、仓库无 description。
- **处置建议**：`git push --force origin main` + `git push --force origin
  refs/tags/*`（14 tag 全量覆盖）→ `gh release view` 核实 Release 指针
  （targetCommitish=main，随 tag 名）→ `ls-remote` 复核。残余风险：GitHub 缓存
  层对旧 SHA 的短暂可达性（必要时联系 support）；第三方历史克隆不可追溯。
  上轮 STATUS 已记录用户对三件套（含强推）的预授权，但本轮出现两项新信息
  （网络恢复、P3-2 决策项可能要求先行重写身份），故仍待最终确认再执行。

### P2-1 CHANGELOG 未发版区段与 `git log` 失同步（违反维护约定 #8）

## 五、根因归纳与机制化建议（本轮新增认知）

1. **扫描器覆盖模型盲区**：内容扫描器只覆盖「跟踪文件 + 历史 blob」；
   安全审计的完整面至少还需：提交元数据（作者/邮箱/message）、未跟踪文件、
   **远端引用状态**。其中「远端是否仍在旧历史上」是处置完成的决定性判据，
   本轮起列为审计必查项（`ls-remote` 本地/远端 SHA 对照）。
2. **状态声称的时间漂移**：「网络不可达」「区段为空」等声称随时间失效；
   收尾/汇报前对声称类硬事实（网络/远端/区段内容/文件数）逐条现场复测，
   不沿用先前结论（本轮正是靠复测发现网络已恢复、待办可立即执行）。
3. **非发版期多提交阶段的登记缺口**：贯穿任务（安全处置）产生多个提交但
   不发版时，未发版区段极易漏登；收尾核对必须 `git log <tag>..HEAD` 逐条比对
   （维护约定 #8 已有要求，本轮证实其应作为审计必查项执行）。
